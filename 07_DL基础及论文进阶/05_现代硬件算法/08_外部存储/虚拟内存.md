# 虚拟内存

早期的操作系统赋予每个进程随意读取和修改任何内存区域的自由，包括那些分配给其他进程的区域。虽然这让事情保持简单，却也带来了一些问题：

- 如果其中一个进程有 bug 或是彻底的恶意程序，该怎么办？我们如何防止它修改分配给其他进程的内存，同时又能保持通过内存进行的进程间通信？
- 我们如何处理内存碎片？假设我们有 4MB 内存，进程 A 为自己分配了前 1MB，接着进程 B 占用了接下来的 2MB，然后 A 终止并释放了它的内存，随后进程 C 到来，请求一段连续的 2MB 区域——但它无法得到，因为我们手里只有两块分离的 1MB 碎片。重启进程 B、或以某种方式暂停它并把它的所有数据和指针整体偏移一兆字节，似乎都不是好办法。
- 我们如何访问非 RAM 类型的内存？我们如何插上一块闪存盘，并从中读取某个特定文件？

这些问题对某些专用计算机系统（例如 GPU）而言并不那么关键，因为你在上面通常一次只解决一个任务、并对计算有完全的控制；但它们对于现代多任务操作系统而言绝对必不可少——而操作系统用一种称为*虚拟内存*的技术解决了所有这些问题。

### 内存分页

虚拟内存让每个进程都以为自己完全掌控着一段连续的内存区域，而这段区域在现实中可能被映射到物理内存的多个较小的块上——其中既包括主存（RAM），也包括外部存储（HDD、SSD）。

![](img/virtual-memory.jpg)

为了实现这一点，内存地址空间被划分为*页*（page，通常大小为 4KB），它们是程序能向操作系统请求的基本内存单元。内存系统维护着一个称为*页表*（page table）的特殊硬件数据结构，其中包含虚拟页地址到物理页地址的映射。当进程使用其虚拟内存地址访问数据时，内存系统会计算出它的页号（如果页大小为 $4096=2^{12}$，就把它右移 $12$ 位），在页表中查到它的物理地址，并把读或写请求转发到数据实际存储的位置。

由于地址转换需要对每次内存请求都执行，而内存页本身的数量可能很大（例如 16G RAM / 4K 页大小 = 4M 页），地址转换本身就是一个难题。加速的一种方法，是为页表本身使用一个称为*转译后备缓冲器*（translation lookaside buffer，TLB）的特殊缓存；另一种方法则是[[内存分页.md|增大页大小]]，从而以牺牲粒度为代价，使内存页的总数变小。

### 映射外部存储

虚拟内存的机制同样能让外部存储类型的使用变得相当透明。现代操作系统支持[内存映射](https://en.wikipedia.org/wiki/Mmap)，它让你可以打开一个文件、并像它在主存中一样使用其内容：

```c++
// open a file containing 1024 random integers for reading and writing
int fd = open("input.bin", O_RDWR);
// map it into memory      size  allow reads and writes  write changes back to the file
int* data = (int*) mmap(0, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
// sort it like if it was a normal integer array
std::sort(data, data + 1024);
// changes are eventually propagated to the file
```

这里映射了一个 4K 的文件，它完全可以放进单独一页内存中；但当我们打开更大的文件时，它的读取会在我们请求某一页时惰性地进行，而它的写入会被缓冲，并在操作系统决定时（通常是在程序终止或系统内存耗尽时）提交到文件系统。

与这一机制运作原理相同、但意图相反的技巧是*交换文件*（swap file），它让操作系统在真实 RAM 不足时，自动把 SSD 或 HDD 的一部分当作主存的扩展来使用。这让内存耗尽的系统的表现从崩溃变成仅仅是严重的减速。

主存与外部存储的这种无缝融合，实质上把 RAM 变成了外部存储的"L4 缓存"，从算法设计的角度，这是一种便利的思考方式。
