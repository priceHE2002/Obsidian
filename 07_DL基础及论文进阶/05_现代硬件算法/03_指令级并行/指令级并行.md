# 指令级并行

程序员一听到"并行（parallelism）"这个词，首先想到的多半是*多核并行*（multi-core parallelism）——有意识地把一个计算拆分成若干半独立的*线程*，协同求解同一个问题。

这种并行主要用于降低*延迟*、实现*可扩展性*（scalability），而非提升*效率*。用并行算法处理规模大十倍的问题，需要消耗的算力资源至少也得多十倍。尽管并行硬件正变得[[现代硬件.md|愈发充裕]]，并行算法设计也愈发重要，但本书目前只讨论单个 CPU 核心。

然而，CPU 核心内部还存在着另一些并行形式，你可以*免费*加以利用。

### 指令流水线

要执行*任意*一条指令，处理器都得先做大量准备工作，包括：

- **取指**（fetching）：从内存取回一段机器码；
- **译码**（decoding）：将其拆解为指令；
- **执行**（executing）这些指令，其中可能涉及若干**内存**操作；
- 将**结果写回**（writing）寄存器。

这一整套流程相当*长*。即便是把两个寄存器中的值 `add` 起来这种简单操作，也要消耗多达 15–20 个 CPU 周期。为了掩盖这一延迟，现代 CPU 采用*流水线*（pipelining）：一条指令刚走完第一个阶段，立刻开始处理下一条，而不必等上一条完全结束。

![](img/pipeline.png)

流水线并不降低*实际*延迟，但在功能上让整体看上去仿佛只剩"执行"和"内存"两个阶段。你仍需付出这 15–20 个周期，只是找到待执行指令序列之后，只需付出一次。

有鉴于此，硬件厂商更倾向用*每指令周期数*（CPI，cycles per instruction）而非"平均指令延迟"作为 CPU 设计的主要性能指标。若只考虑*有用*指令，它对算法设计也是[[基准测试.md|相当不错的指标]]。

理想流水线的 CPI 应当趋近于 1，但若把流水线的每个阶段"加宽"（复制一份），使同一时刻能处理多于一条指令，它实际上还能更低。由于缓存与大部分 ALU 可以共享，这比新增一个完全独立的核心更划算。这种每个周期能执行多于一条指令的架构称为*超标量*（superscalar），现代 CPU 大多如此。

唯有当指令流中包含若干逻辑上相互独立、可分别处理的操作组时，才能利用超标量处理。指令并非总以最便利的顺序抵达，因此在可能时，现代 CPU 会*乱序*（out of order）执行它们，以提升整体利用率、减少流水线停顿。这套"魔法"如何实现，属于更深入的话题<!--[a more advanced discussion](scheduling)-->，但眼下你可以假定：CPU 维护着一个延伸到未来一定距离的待执行指令缓冲，一旦某条指令的操作数算好、且有空闲的执行单元，便立刻执行它。

### 一个教育类比

不妨看看现行的教育体系如何运作：

1. 授课以学生群体而非个人为单位，因为把相同内容广播给所有人更高效。
2. 新生被分成由不同老师带领的小组；作业与其他课程资料在各组间共享。
3. 每年同一门课都教给新一届学生，使老师们始终有事可做。

这些革新大幅提升了整个系统的*吞吐率*，而*延迟*（某位学生从入学到毕业的时间）保持不变（甚至可能略升，因为个性化辅导更高效）。

其与现代 CPU 的相似之处比比皆是：

1. CPU 利用 [[SIMD并行.md|SIMD 并行]] 对同一批不同数据点（16、32 或 64 字节）执行相同操作。
2. 多个执行单元可同时处理这些指令，并共享其他 CPU 设施（通常 2–4 个执行单元）。
3. 指令以流水线方式处理（节省的周期数，大致等于从幼儿园到博士的年限）。

此外，还有若干方面也吻合：

- 执行路径随时间愈发分化，需要不同的执行单元。
- 某些指令可能因种种原因停顿。
- 某些指令甚至被推测执行（提前执行）后又被丢弃。
- 某些指令可能被拆成若干独立的微操作，各自推进。

为流水线化与超标量的处理器编程有其特有的挑战，这正是本章要探讨的内容。
