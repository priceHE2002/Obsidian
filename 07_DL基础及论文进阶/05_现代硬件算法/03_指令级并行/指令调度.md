# 指令调度

让我们再深入一点。

### 超标量处理器

理想流水线的 CPI 应当趋近于 1，但它实际上还能低于 1。

由于指令种类繁多，程序中常常出现若干逻辑上相互独立、可由不同执行单元分别处理的操作组。为提升其利用率，我们可以复制流水线的其余部分，使同一时刻能处理多于一条指令，并在可能时把这些指令调度到 ALU 的不同部分上。这种每个周期能执行多于一条指令的架构称为*超标量*（superscalar），现代 CPU 大多如此。

<!-- Pipeline of a superscalar CPU with the width of 2 img/superscalar.png -->

把执行的各个阶段交错开来，是数字电路中的一种通用思路，它不仅应用于主 CPU 流水线，也应用于单独指令与[[内存级并行.md|内存]]的层面。多数执行单元都有自己的小流水线，能在前一条指令之后仅一两个周期就接收下一条指令。如果某条指令使用频繁，把它对应的执行单元也复制一份是合情合理的，同时也把经常联合使用的指令放在同一个执行单元上：例如，别把算术操作和内存操作放在同一个单元上。

### 微码

复杂的指令集虽有好处，但就超标量处理器而言，你希望指令尽可能细小且原子化。比如融合的加法指令。这也提供了一种简便方式，用来"淘汰"那些无人使用、你也不想再支持的旧指令：只需用上百条左右的微码指令替换它们即可。反正本来也没人用。

指令是被微码化的。

uOps（"微操作"，micro-ops，首字母本意是希腊字母 mu，如同 us（微秒）中的那样，但没人在乎去把它打出来）。

每种架构都有自己的一组"端口"（ports），每个端口能执行自己的一组指令（更准确地说是 uOps）。

但当你使用它时，它给人的感觉仍像一条单独的指令。CPU 是如何做到这一点的？

### 指令调度

这给协调"如何执行指令、以什么顺序执行"带来了额外的挑战。正因如此，现代调度器占用的芯片面积比整个整数 ALU 还大。它们复杂得令人发指，但这个心智模型在大多数时候已经足够好用。

现代处理器实际上并非逐条执行指令，而是维护着一个*流水线*式的待执行指令队列，使两条独立操作能并发执行，而无须互相等待对方完成。

乱序执行。一个待执行指令的缓冲。

更精确一点说，CPU 会向前窥探指令流，直到未来某个距离。若有分支，它会做分支预测，从而产出一条连续的指令流。然后它会判断哪些指令已经就绪、可以执行。例如，如果它看到未来某条指令 X 只用到寄存器 A 和 B，而在它之前没有任何指令触碰这两个寄存器，当前流水线里也没有任何指令修改这两个寄存器，那么只要一有空闲的执行单元，就可以放心地开始执行 X。

这一切都发生在硬件内部，无时无刻、全自动进行。程序员唯一要做的，就是保证始终有充分多的独立指令可供执行。魔法发生在 CPU 内部。编译器只是生成两条机器语言指令，不带任何标注来表明这些指令能否并行执行。CPU 随后会自动判断哪些指令可以并行执行。

你可以分别调度独立指令，但只能到一定程度。这个缓冲很大，可容纳数百条操作。但对于像主存访问这样特别长的操作，仍不够用。
