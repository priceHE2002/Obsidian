# 指令表

<!-- This poses some additional challenges in coordinating how to execute the instructions — and also in which order. -->

把执行的各个阶段交错开来，是数字电路中的一种通用思路，它不仅应用于主 CPU 流水线，也应用于单独指令与[[内存级并行.md|内存]]的层面。多数执行单元都有自己的小流水线，能在前一条指令之后仅一两个周期就接收下一条指令。

在此语境下，对指令使用两种不同的"[[复杂性模型.md|开销]]"是合宜的：

- *延迟*（Latency）：收到一条指令的结果需要多少个周期。
- *吞吐*（Throughput）：平均每周期能执行多少条指令。

<!-- alternative throughput definitions, maybe in scheduling? -->

你可以从一种名为[指令表](https://www.agner.org/optimize/instruction_tables.pdf)（instruction tables）的专用文档中，查到特定架构的延迟与吞吐数值。下面是我这台 Zen 2 的一些示例值（如有差异，一律按 32 位操作数给出）：

| 指令 | 延迟 | 倒数吞吐 |
|-------------|---------|:------------|
| `jmp`       | -       | 2           |
| `mov r, r`  | -       | 1/4         |
| `mov r, m`  | 4       | 1/2         |
| `mov m, r`  | 3       | 1           |
| `add`       | 1       | 1/3         |
| `cmp`       | 1       | 1/4         |
| `popcnt`    | 1       | 1/4         |
| `mul`       | 3       | 1           |
| `div`       | 13-28   | 13-28       |

几点说明：

- 由于我们的思维太习惯"多即更糟"的开销模型，人们大多使用吞吐的*倒数*而非吞吐本身。
- 如果某条指令特别频繁，可以复制它的执行单元来提升吞吐——甚至可能提升到大于 1，但高不过[[机器码布局.md|译码宽度]]。
- 有些指令的延迟为 0。这意味着这些指令用于控制调度器，不会到达执行阶段。它们仍有非零的倒数吞吐，因为[[机器码布局.md|CPU 前端]]仍需处理它们。
- 多数指令是流水化的，若其倒数吞吐为 $n$，通常意味着它的执行单元在 $n$ 个周期后可接收下一条指令（若小于 1，则意味着存在多个执行单元，都能在下一周期接收新指令）。一个显著的例外是[[整数除法.md|整数除法]]：它的流水化程度极差，或者根本没流水化。
- 有些指令的延迟是可变的，不仅取决于操作数大小，也取决于其值。对于内存操作（包括 `add` 这样的融合操作），其延迟通常按最优情况（L1 缓存命中）给出。

还有更多重要的细枝末节，但眼下这个心智模型已经够用。
