# 吞吐量计算

为*延迟*做优化，通常与为*吞吐*做优化大不相同：

- 当优化数据结构查询、一次性小规模或带分支的算法时，你需要[[指令表.md|查阅其指令的延迟]]，在脑中构建计算的执行图，然后试着重组它，使关键路径更短。
- 当优化热点循环与大规模数据集算法时，你需要查阅其指令的吞吐，统计每次迭代每条指令被使用的次数，判断哪条是瓶颈，然后试着重组循环，让它被用得更少。

最后这条建议只对*数据并行*循环有效，即每次迭代与上次完全独立。当连续迭代之间存在某种相互依赖时，就可能因下一次迭代等待上一次完成而引发一次由[[流水线冒险.md|数据冒险]]造成的流水线停顿。

### 例子

作为一个简单例子，考虑数组求和是如何计算的：

```c++
int s = 0;

for (int i = 0; i < n; i++)
    s += a[i];
```

先假设编译器没有对循环做[[SIMD并行.md|向量化]]，[[内存带宽.md|内存带宽]]不成问题，而且循环已被[[循环与条件分支.md|展开]]，因此无需为维护循环变量付出额外开销。此时计算变得非常简单：

```c++
int s = 0;
s += a[0];
s += a[1];
s += a[2];
s += a[3];
// ...
```

我们能算多快？恰好每元素一个周期——因为每次迭代都需要一个周期把另一个值 `add` 到 `s`。内存读取的延迟无关紧要，因为 CPU 可以提前启动它。

但我们还能更高。在我的 CPU（Zen 2）上，`add` 的*吞吐*是 2，意味着理论上每周期可执行两条。但眼下这不可能：当 `s` 正被用来累加第 $i$ 个元素时，它至少要一个周期之后才能用于第 $(i+1)$ 个。

[^throughput]: 寄存器-寄存器 `add` 的吞吐是 4，但由于第二个操作数从内存读取，它受内存 `mov` 的吞吐制约，在 Zen 2 上为 2。

解决办法是用*两个*累加器，把奇数与偶数元素分开求和：

```c++
int s0 = 0, s1 = 0;
s0 += a[0];
s1 += a[1];
s0 += a[2];
s1 += a[3];
// ...
int s = s0 + s1;
```

现在我们的超标量 CPU 能同时执行这两条"线程"，计算不再有任何限制吞吐的关键路径。

### 一般情况

若一条指令的延迟为 $x$、吞吐为 $y$，则需要使用 $x \cdot y$ 个累加器才能使其饱和。这也意味着需要 $x \cdot y$ 个逻辑寄存器来保存它们的值，这对 CPU 设计是个重要考量，限制了可用于高延迟指令的执行单元的最大数量。

这项技术主要用于 [[SIMD并行.md|SIMD]]，而非标量代码。你可以[[归约.md|推广]]上面的代码，比编译器更快地计算求和及其他归约。

一般而言，优化循环时，你通常只有一个或少数几个*执行端口*希望被充分利用，并围绕它们来设计循环的其余部分。由于不同指令可能使用不同的端口集合，究竟哪个会被过度使用并不总是分明。在这种情形下，[[机器码分析器.md|机器码分析器]]对寻找小型汇编循环的瓶颈很有帮助。
