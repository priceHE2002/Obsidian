# 何时该做优化

为什么像谷歌这样的公司会在面试中要求候选人在白板上解决算法问题？

原因在于，拥有超过一万名工程师的组织与外部世界大不相同。

当然，随着职业发展，这些编程问题会被复杂的系统设计问题和领导能力评估所取代。只是眼下这还无关紧要，因为你刚从大学毕业还不会直接进入高级职位。

这大体只是我对性能工程职业路径的随想。

大部分计算机科学知识都被高层语言和库抽象掉了。

我假设你要么想在业界工作，要么想在学术界做点真正有用的事。

算法设计是一种你 20% 的时间会用到、却决定了 80% 成败的技能。

有些领域里性能是决定性的杀手锏特性。但看看 Java 生态：它慢得要命，却仍然支撑着大部分大数据生态，并运行着大部分 Android 应用。Java 以及其他基于虚拟机的语言（如 WebAssembly）短期内都不会消失。

当然，招聘中也存在大量 ~~愚蠢~~ 偏见。有些大公司根本不问这类问题，也有完全由前竞赛选手或现役竞赛选手组成的公司。这很合理，因为如果人们认为某项技能被低估，他们为何要雇佣具备该技能的人，反之亦然。

无论如何，大 O 记号并不是公司真正想要的。重点不在于写出最优的问题解法——更在于避免极其缓慢的解法。也就是那些无法扩展的解法。计算力确实在持续变得更廉价。

如果你有过竞赛编程的经历，你会格外感到沮丧。即便面试中问到了这类问题，你也不会有机会去解它们。要解决它们，你需要另一种资质。渐近最优的算法已经存在，你需要优化的是常数因子。不幸的是，只有少数几所大学会教这个。

## 优化的层次

按软件优化能力，程序员可以被划分到若干"层次"：

0. *新手（Newbie）*。那些完全不考虑性能的人。他们通常用高层语言编程，有时用声明式 / 函数式语言。大多数"程序员"停留在此（这并没有什么不对）。
1. *本科生（Undergraduate student）*。那些了解大 O 记号、熟悉基本数据结构与方法的人。LeetCode 和 CodeForces 玩家在此之列。这也是进入大公司的要求——它们有大量内部软件、大规模系统，并且着眼于长期用人，所以会考察编程语言之类的东西。
2. *研究生（Graduate student）*。那些知道并非所有操作生而平等；了解其他代价模型，如外部存储模型（B 树、外部排序）、字模型（位集），或并行计算，但仍是停留在理论层面。
3. *专业开发者（Professional developer）*。那些知道这些操作的实际耗时。意识到分支预测失败（branch mispredictions）代价高昂，内存被拆分为缓存行。了解一些基本的 SIMD 技术。
4. *性能工程师（Performance engineer）*。确切知道自己的硬件内部发生了什么。知道延迟与带宽的区别，了解端口（ports）。知道如何有效使用 SIMD 和指令集的其余部分。能读懂汇编并使用性能剖析工具。
5. *英特尔员工（Intel employee）*。了解微架构层面的具体细节。这超出了普通工程师的职责范围。

在本书中，我们预期普通读者大致处于第 1 阶段，并希望在读完本书后能到达第 4 阶段。

在设计算法时，你也应该经历这些层次。首先让它先能跑起来，然后选择一批渐近最优性合理的算法。接着思考它们在内存操作或并行执行能力方面的表现（即便你考虑的是单线程程序，核心内部仍会有大量并行性，因此这一模型极为……），然后进入实际实现。如 Knuth 所言，避免过早优化。

对大多数 Web 服务而言，效率无关紧要，但延迟（latency）要紧。

提升效率已不是当今的做法。

一次页面浏览通常带来约 0.1 到 1 美分的收入。这是你将用户注意力变现的典型速率。比方说，如果我简单地装上 AdSense，就能获得大致这样的收入——具体取决于我大多数读者来自哪里，以及其中有多少人使用了广告屏蔽器。

与此同时，一台拥有专用核心和 1GB 内存的服务器（对简单 Web 服务而言是荒谬地庞大的资源量），在摊还后每秒成本约为百万分之一美元。用这些钱你可以取回 100 张照片。

亚马逊曾做过一个实验，他们对服务进行人工延迟的 A/B 测试，发现 100 毫秒的延迟会降低收入。这对大多数其他服务也一样成立，例如，你在推特上"断流"了，用户就很可能会开始想别的事然后离开。如果谷歌的延迟超过几秒，人们会直接认为谷歌坏了并退出。

延迟的最小化通常可以通过并行计算来实现，这也就是为什么分布式系统更多地在可扩展性上扩展。本书的这一部分关注于提升算法的效率（efficiency），而延迟降低只是其副产品。

然而，仍有一些使用场景需要在质量与服务器成本之间权衡。

- 搜索是分层的。通常存在许多层更精确但更慢的模型。你在每一层排序的文档越多，最终质量就越好。
- 游戏。它们在大规模下更有趣，但算力也在增长。这包括 AI。
- AI 工作负载——那些拥有海量数据（如语言模型）的工作负载。更重的模型需要更多算力。它们的瓶颈不在于数据量，而在于效率（efficiency）。

本质串行的算法，或资源受限的情况。在大 PDF 里按 Ctrl+f 查找很痛苦。因式分解（Factorization）也是如此。

## 评估影响

有时优化需要发生在调用层。

SIMDJSON 加速了 JSON 解析，但一开始就不使用 JSON 或许更好。

Protobuf 或扁平二进制格式。

还存在一个鸡生蛋、蛋生鸡的问题：人们不太用某种方法，是因为它慢且不可行。

实现成本、缺陷、可维护性。世界上大多数软件效率低下，这完全没问题。

成为一名更好的程序员意味着什么？更快的程序？更快的工作效率？更少的缺陷？它是这些要素的组合。

实现编译器优化或数据库，都是高杠杆（high-leverage）活动的例子，因为它们就像对一切征收的"税"——这也解释了为什么你看到大多数人写的是这些特定主题的书，而不是泛泛的软件优化。
