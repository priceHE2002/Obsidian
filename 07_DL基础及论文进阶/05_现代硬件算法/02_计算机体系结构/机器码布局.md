# 机器码布局

计算机工程师喜欢在脑中把 [[指令级并行.md|CPU 的流水线]] 分成两部分：*前端*（front-end），指令从这里被从内存取回并解码；以及*后端*（back-end），指令在这里被调度并最终执行。通常性能瓶颈在执行阶段，正因如此，本书中我们的多数精力将花在围绕后端做优化上。

但有时情况会反转，当前端不能以足够快的速度向后端输送指令使其饱和时。这可能由多种原因造成，最终都与机器码在内存中如何布局有关，并以种种轶事般的方式影响性能，例如移除未使用的代码、交换「if」分支，甚至改变函数声明的顺序，都会导致性能或升或降。

### CPU 前端

在机器码被转换成指令、CPU 理解程序员意图之前，它首先需要经过两个我们感兴趣的重要阶段：*取指*（fetch）与*解码*（decode）。

在 **fetch（取指）** 阶段，CPU 简单地从主存加载一块固定大小的字节，其中包含若干指令的二进制编码。这个块大小在 x86 上通常是 32 字节，尽管在不同机器上可能变化。一个重要的细微之处是，这个块必须是 [[缓存行.md|对齐]] 的：块的地址必须是其大小的整数倍（在我们的例子中是 32B）。

接下来是 **decode（解码）** 阶段：CPU 查看这块字节，丢弃指令指针之前的一切，把其余部分切分成指令。机器指令用可变数量的字节编码：像 `inc rax` 这样简单且非常常见的指令只占一个字节，而某些带有编码常量和改变行为前缀的冷僻指令最多可能占 15 个字节。因此从一个 32 字节的块中可能解码出数量可变的指令，但不超过一个机器相关的上限，称为*解码宽度*（decode width）。在我的 CPU（一款 [Zen 2](https://en.wikichip.org/wiki/amd/microarchitectures/zen_2)）上，解码宽度是 4，意味着每个周期最多可解码 4 条指令并传给下一阶段。

这些阶段以流水线方式工作：如果 CPU 能判断（或 [[分支的代价.md|预测]]）它下一步需要哪块指令，那么取指阶段就不会等待当前块中的最后一条指令解码完，而是立即加载下一块。

### 代码对齐

在其他条件相同的情况下，编译器通常偏好机器码更短的指令，因为这样更多的指令能放进单个 32B 的取指块中，也因为这样能减小二进制文件的体积。但有时情况恰恰相反更为可取，原因是所取出的指令块必须是对齐的。

设想你需要执行一个从 32B 对齐块的最后一个字节开始执行的指令序列。你或许能无额外延迟地执行第一条指令，但对其后的指令，你必须为再一次取指多等一个周期。如果代码块是在 32B 边界上对齐的，那么最多可以有 4 条指令被解码并随后并发执行（除非它们特别长或相互依赖）。

考虑到这一点，编译器经常会做一种看似有害的优化：它们有时偏好机器码更长的指令，甚至插入什么都不做的哑指令[^nop]，以便把关键跳转位置对齐到合适的 2 的幂边界。

[^nop]: 这类指令称为空操作，或 NOP 指令。在 x86 上，「官方」什么都不做的方式是 `xchg rax, rax`（把一个寄存器与自身交换）：CPU 能识别它，除了在解码阶段外不会多花周期去执行它。`nop` 简写映射到相同的机器码。

在 GCC 中，你可以用 `-falign-labels=n` 标志指定特定的对齐策略，[替换](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html) 其中的 `-labels` 为 `-function`、`-loops` 或 `-jumps` 即可更有选择性。在 `-O2` 和 `-O3` 优化级别，它默认开启——但不设定具体对齐，此时使用一个（通常合理的）机器相关默认值。

### 指令缓存

指令的存储与取回使用的是大体上与数据相同的 [[RAM与CPU缓存.md|内存系统]]，只是可能把缓存的较低层替换为一个独立的*指令缓存*（因为你不希望一次随机的数据读取把处理它的代码踢出去）。

指令缓存在以下两种情形中至关重要：

- 你不知道接下来要执行什么指令，需要以 [[内存延迟.md|低延迟]] 取回下一块；
- 或者你正在执行一长串啰嗦但处理起来很快的指令，需要 [[内存带宽.md|高带宽]]。

因此内存系统可能成为机器码庞大的程序的瓶颈。这一考量限制了我们之前讨论的那些优化技术的适用性：

- [[函数与递归.md|内联函数]] 并非总是最优，因为它降低了代码共享并增大了二进制体积，从而需要更多指令缓存。
- [[循环与条件分支.md|循环展开]] 即便在迭代次数编译期已知的情况下，也只在某种程度上有益：到了某个点，CPU 将不得不同时从主存取指令和数据，此时它很可能被内存带宽所瓶颈。
- 巨大的 [代码对齐](#代码对齐) 会增加二进制体积，再次需要更多指令缓存。与错过缓存、等待指令从主存取回相比，在取指上多花一个周期只是微小的代价。

另一个方面是，把频繁使用的指令序列放在相同的 [[缓存行.md|缓存行]] 和 [[内存分页.md|内存页]] 上能改善 [[时空局部性.md|缓存局部性]]。为了提升指令缓存利用率，你应当把热代码与热代码、冷代码与冷代码归在一起，并尽可能移除死（未使用）代码。如果你想进一步探索这个思路，可以看看 Facebook 的 [Binary Optimization and Layout Tool](https://engineering.fb.com/2018/06/19/data-infrastructure/accelerate-large-scale-applications-with-bolt/)，它最近被 [合并](https://github.com/llvm/llvm-project/commit/4c106cfdf7cf7eec861ad3983a3dd9a9e8f3a8ae) 进了 LLVM。

### 不等分支

设想出于某种原因你需要一个辅助函数来计算整数区间的长度。它接收两个参数 $x$ 和 $y$，但为了方便，它可能对应 $[x, y]$ 或 $[y, x]$，取决于哪一侧非空。在纯 C 中你大概会写成这样：

```c++
int length(int x, int y) {
    if (x > y)
        return x - y;
    else
        return y - x;
}
```

在 x86 汇编中，如何实现它有更多样的选择，并显著影响性能。我们先试着把这段代码直接映射到汇编：

```nasm
length:
    cmp  edi, esi
    jle  less
    ; x > y
    sub  edi, esi
    mov  eax, edi
done:
    ret
less:
    ; x <= y
    sub  esi, edi
    mov  eax, esi
    jmp  done
```

虽然最初的 C 代码看起来非常对称，汇编版本却不是。这导致一个有趣的怪现象：一个分支能比另一个略快地被执行的：如果 `x > y`，那么 CPU 可以只执行 `cmp` 与 `ret` 之间的 5 条指令，如果函数是对齐的，它们都会被一次性取回；而在 `x <= y` 的情况下，则需要再多两次跳转。

我们有理由假设 `x > y` 的情况是*不可能*发生的（谁会去计算一个反转区间的长度呢？），它更像是一个几乎从不发生的例外。我们可以检测到这种情况，并简单地交换 `x` 和 `y`：

```c++
int length(int x, int y) {
    if (x > y)
        swap(x, y);
    return y - x;
}
```

汇编会像下面这样，正如 if 不带 else 模式通常所发生的那样：

```nasm
length:
    cmp  edi, esi
    jle  normal     ; if x <= y, no swap is needed, and we can skip the xchg
    xchg edi, esi
normal:
    sub  esi, edi
    mov  eax, esi
    ret
```

指令总长度现在是 6，从 8 降了下来。但它仍不是针对我们假设情形真正优化的：如果我们认为 `x > y` 永不发生，那么加载那条永远不会被执行的 `xchg edi, esi` 指令就是一种浪费。我们可以通过把它移出正常执行路径来解决：

```nasm
length:
    cmp  edi, esi
    jg   swap
normal:
    sub  esi, edi
    mov  eax, esi
    ret
swap:
    xchg edi, esi
    jmp normal
```

这项技术在一般处理例外情形时相当顺手，而在高层代码中，你可以给编译器一个 [[情境化优化.md|提示]]，表明某个分支比另一个更可能执行：

```c++
int length(int x, int y) {
    if (x > y) [[unlikely]]
        swap(x, y);
    return y - x;
}
```

这项优化只有当你知道某个分支极少被采用时才有好处。若非如此，还有比代码布局更重要的 [[流水线冒险.md|其他方面]]，迫使编译器完全避免任何分支——在此情形下，用一条特殊的「条件传送」（conditional move）指令来替代它，大致对应于三元表达式 `(x > y ? y - x : x - y)` 或调用 `abs(x - y)`：

```nasm
length:
    mov   edx, edi
    mov   eax, esi
    sub   edx, esi
    sub   eax, edi
    cmp   edi, esi
    cmovg eax, edx  ; "mov if edi > esi"
    ret
```

消除分支是一个重要主题，我们将在 [[分支的代价.md|下一章大量篇幅]] 中更详细地讨论它。
