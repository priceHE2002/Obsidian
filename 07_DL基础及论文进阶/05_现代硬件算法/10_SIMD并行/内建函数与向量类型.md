# 内建函数与向量类型

使用 SIMD 最底层的方式是直接用汇编向量指令——它们与其标量等价物毫无区别——但我们不打算这样做。相反，我们将使用映射到这些指令上的*内建*（intrinsic）函数，它们在现代 C/C++ 编译器中均可使用。

本节中，我们将过一遍它们语法的基础，而在本章其余部分，我们会大量使用它们来做真正有趣的事情。

## 准备工作

要使用 x86 内建函数，我们需要做一些基础工作。

首先，我们需要确定硬件支持哪些扩展。在 Linux 上，你可以调用 `cat /proc/cpuinfo`，而在其他平台上，你最好去 [WikiChip](https://en.wikichip.org/wiki/WikiChip)，用 CPU 的名称去查。无论哪种情况，都应该有一个 `flags` 段，列出了所有受支持的向量扩展的代码。

还有一个特殊的 [CPUID](https://en.wikipedia.org/wiki/CPUID) 汇编指令，可以让你查询关于 CPU 的各类信息，包括特定向量扩展的支持情况。它主要用于在运行时获取这类信息，从而避免为每种微架构分发独立的二进制文件。它的输出信息以特征掩码（feature mask）的形式非常密集地返回，所以编译器提供了内建方法来解读它。下面是一个例子：

```c++
#include <iostream>
using namespace std;

int main() {
    cout << __builtin_cpu_supports("sse") << endl;
    cout << __builtin_cpu_supports("sse2") << endl;
    cout << __builtin_cpu_supports("avx") << endl;
    cout << __builtin_cpu_supports("avx2") << endl;
    cout << __builtin_cpu_supports("avx512f") << endl;

    return 0;
}
```

其次，我们需要包含一个头文件，其中含有我们所需的那部分内建函数。类似于 GCC 中的 `<bits/stdc++.h>`，存在一个 `<x86intrin.h>` 头文件包含了它们全部，所以我们直接用这个即可。

最后，我们需要[[编译选项与目标平台.md|告诉编译器]]目标 CPU 确实支持这些扩展。这可以通过 `#pragma GCC target(...)` [[SIMD并行.md|像我们之前那样]]，或者通过编译器选项中的 `-march=...` 标志来完成。如果你在同一台机器上编译并运行代码，可以设置 `-march=native` 来自动检测微架构。

在之后所有的代码示例中，假设它们都以这些行开头：

```c++
#pragma GCC target("avx2")
#pragma GCC optimize("O3")

#include <x86intrin.h>
#include <bits/stdc++.h>

using namespace std;
```

在本章中我们将聚焦于 AVX2 以及之前的 SIMD 扩展，它们应该能在 95% 的桌面与服务器计算机上可用，尽管一般原理同样适用于 AVX512、Arm Neon 以及其他 SIMD 架构。

### SIMD 寄存器

SIMD 扩展之间最显著的差别在于对更宽寄存器的支持：

- SSE（1999）增加了 16 个 128 位寄存器，命名为 `xmm0` 到 `xmm15`。
- AVX（2011）增加了 16 个 256 位寄存器，命名为 `ymm0` 到 `ymm15`。
- AVX512（2017）增加了[^mask] 16 个 512 位寄存器，命名为 `zmm0` 到 `zmm15`。

[^mask]: AVX512 还增加了 8 个所谓的*掩码寄存器*，命名为 `k0` 到 `k7`，用于掩码与混合数据。我们不会覆盖它们，而将主要使用 AVX2 及之前的标准。

正如你可以从命名中猜到的那样，并且考虑到 512 位已经占据整整一条缓存行，x86 设计者近期不打算增加更宽的寄存器。

C/C++ 编译器实现了特殊的*向量类型*（vector type），用于指代存储在这些寄存器中的数据：

- 128 位的 `__m128`、`__m128d` 和 `__m128i` 类型，分别用于单精度浮点、双精度浮点以及各类整数数据；
- 256 位的 `__m256`、`__m256d`、`__m256i`；
- 512 位的 `__m512`、`__m512d`、`__m512i`。

寄存器本身可以容纳任意类型的数据：这些类型仅用于类型检查。你可以像转换任何其他类型一样，将一个向量变量转换为另一个向量类型，这不会带来任何代价。

### SIMD 内建函数

*内建函数*（intrinsics）只是一些对向量数据类型做某些操作的 C 风格函数，通常只是简单地调用关联的汇编指令。

例如，下面是一个用 AVX 内建函数将两个 64 位浮点数数组相加的循环：

```c++
double a[100], b[100], c[100];

// 以 4 个为一块迭代，
// 因为 256 位寄存器正好能容纳这么多 double
for (int i = 0; i < 100; i += 4) {
    // 将两个 256 位段载入寄存器
    __m256d x = _mm256_loadu_pd(&a[i]);
    __m256d y = _mm256_loadu_pd(&b[i]);

    // 将 4+4 个 64 位数相加
    __m256d z = _mm256_add_pd(x, y);

    // 将 256 位结果写入内存，从 c[i] 开始
    _mm256_storeu_pd(&c[i], z);
}
```

使用 SIMD 的主要难点在于把数据装入适合载入寄存器的、连续的、固定大小的块中。在上面的代码中，如果数组长度不能被块大小整除，一般来说就会有问题。对此有两种常见的解决方案：

1. 我们可以"越界"一点，无论如何都迭代到最后一个不完整的段。为确保不会因为试图读取或写入不属于我们的内存区域而触发段错误，我们需要将数组补齐到最近的块大小（通常用某个"中性"元素，例如零）。
2. 少做一次迭代，并在最后写一个小小的循环，用标量操作正常计算剩余部分。

人类更喜欢 #1，因为它更简单、产生的代码更少；而编译器更喜欢 #2，因为它们并没有其他合法选择。

### 指令参考

大多数 SIMD 内建函数遵循类似 `_mm<size>_<action>_<type>` 的命名约定，并对应于一条同名（类比命名）的汇编指令。一旦你习惯了汇编命名约定，它们就相对自解释了，尽管有时看起来确实像是猫在键盘上走出来的名字（解释一下：[punpcklqdq](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html#ig_expand=3037,3009,4870,4870,4872,4875,833,879,874,849,848,6715,4845,6046,3853,288,6570,6527,6527,90,7307,6385,5993,2692,6946,6949,5456,6938,5456,1021,3007,514,518,4875,7253,7183,3892,5135,5260,5259,6385,3915,4027,3873,7401&techs=AVX,AVX2&text=punpcklqdq)）。

这里再给几个例子，好让你体会其要旨：

- `_mm_add_epi16`：将两个 128 位向量中的 16 位*扩展打包整数*（extended packed integers）相加，简单说就是 `short`。
- `_mm256_acos_pd`：对 4 个*打包 double*（packed doubles）逐元素计算 $\arccos$。
- `_mm256_broadcast_sd`：将内存中一个 `double` 广播（复制）到结果向量的全部 4 个元素。
- `_mm256_ceil_pd`：将 4 个 `double` 各自向上取整到最近的整数。
- `_mm256_cmpeq_epi32`：比较 8+8 个打包 `int`，并返回一个在相等元素对处含 1 的掩码。
- `_mm256_blendv_ps`：按照掩码从两个向量之一中挑选元素。

正如你可能猜到的，内建函数的数量在组合意义上是极大的，而且除此之外，某些指令还带有立即数——所以它们的内建函数需要编译期常量参数：例如，浮点比较指令[有 32 种不同的修饰符](https://stackoverflow.com/questions/16988199/how-to-choose-avx-compare-predicate-variants)。

出于某种原因，存在一些对寄存器中存储的数据类型不敏感、却只接受特定向量类型（通常是 32 位浮点）的操作——你只需先转换为它、用完再转换回来即可使用那个内建函数。为了简化本章中的例子，我们将主要使用 256 位 AVX2 寄存器中的 32 位整数（`epi32`）。

一个对 x86 SIMD 内建函数非常有用的参考是 [Intel Intrinsics Guide](https://software.intel.com/sites/landingpage/IntrinsicsGuide/)，它按类别与扩展分组，提供描述、伪代码、关联的汇编指令，以及它们在 Intel 微架构上的延迟与吞吐。你大概想把它加入书签。

当你确切知道某条指令存在、只想查它的名字或性能信息时，Intel 参考很有用。当你不知道它是否存在时，这份[速查表](https://db.in.tum.de/~finis/x86%20intrinsics%20cheat%20sheet%20v1.0.pdf)可能更管用。

**指令选择。** 注意，编译器并不一定会挑选你指定的那条精确指令。类似于我们[[汇编语言.md|之前讨论过]]的标量 `c = a + b`，也存在一条融合的向量加法指令，所以编译器不再是每个循环周期用 2+1+1=4 条指令，而是[将上面的代码改写为](https://godbolt.org/z/dMz8E5Ye8) 3 条指令组成的块，如下所示：

```nasm
vmovapd ymm1, YMMWORD PTR a[rax]
vaddpd  ymm0, ymm1, YMMWORD PTR b[rax]
vmovapd YMMWORD PTR c[rax], ymm0
```

有时，尽管相当罕见，这种编译器的"干预"会让事情变得更糟，所以[[编译的各个阶段.md|查看汇编]]、更仔细地审视发出的向量指令（它们通常以 "v" 开头）总是一个好主意。

此外，某些内建函数并不映射到单条指令，而是映射到一小段指令序列，作为一种方便的捷径：[[数据搬移.md#对齐的载入与存储|广播与提取]]就是一个显著的例子。

### GCC 向量扩展

如果你觉得 C 内建函数的设计很糟糕，你并不孤单。我花了数百小时编写 SIMD 代码、阅读 Intel Intrinsics Guide，却仍然记不住到底该写 `_mm256` 还是 `__m256`。

内建函数不仅难用，而且既不便于移植，也难于维护。在优秀的软件中，你不会想为每种 CPU 维护不同的过程：你想以与架构无关的方式只实现一次。

有一天，来自 GNU 项目的编译器工程师们也这样想，于是开发了一种定义你自己的向量类型的方法，它更像是带某些重载运算符以匹配相关指令的数组。

在 GCC 中，下面这样定义一个打包进 256 位（32 字节）寄存器、由 8 个整数组成的向量：

```c++
typedef int v8si __attribute__ (( vector_size(32) ));
// 类型 ^   ^ 类型名         字节数 ^
```

遗憾的是，这不是 C 或 C++ 标准的一部分，所以不同的编译器为此使用不同的语法。

多少存在一种命名约定，即把元素的大小与类型纳入类型名：在上面的例子中，我们定义了一个"8 个有符号整数的向量"。但你可以起任何想要的名字，比如 `vec`、`reg` 之类的。唯一你不该做的事，是把它命名为 `vector`，因为 `std::vector` 会带来极大的混淆。

使用这些类型的主要优势在于，对许多操作你可以用普通的 C++ 运算符，而不必去查相关的内建函数。

```c++
v4si a = {1, 2, 3, 5};
v4si b = {8, 13, 21, 34};

v4si c = a + b;

for (int i = 0; i < 4; i++)
    printf("%d\n", c[i]);

c *= 2; // 乘以标量

for (int i = 0; i < 4; i++)
    printf("%d\n", c[i]);
```

借助向量类型，我们可以极大地简化之前用内建函数实现的 "a + b" 循环：

```c++
typedef double v4d __attribute__ (( vector_size(32) ));
v4d a[100/4], b[100/4], c[100/4];

for (int i = 0; i < 100/4; i++)
    c[i] = a[i] + b[i];
```

如你所见，与内建函数那场噩梦相比，向量扩展要清爽得多。它们的缺点是，有些我们想做的事单纯无法用原生 C++ 构造表达，所以那些情况我们仍需要内建函数。幸运的是，这不是二选一，因为向量类型支持零代价地转换为 `_mm` 类型并转换回来：

```c++
v8f x;
int mask = _mm256_movemask_ps((__m256) x)
```

还有许多针对不同语言的第三方库，提供类似的能力来编写可移植的 SIMD 代码，并且通常比内建函数和编译器的内建向量类型都更好用。C++ 中著名的例子有 [Highway](https://github.com/google/highway)、[Expressive Vector Engine](https://github.com/jfalcou/eve)、[Vector Class Library](https://github.com/vectorclass/version2) 以及 [xsimd](https://github.com/xtensor-stack/xsimd)。

使用成熟的 SIMD 库是推荐的，因为它能极大地改善开发体验。不过，在本书中，我们会尽量贴近硬件，主要直接使用内建函数，偶尔在力所能及之处切换到向量扩展以换取简洁。
