# 编译器的能与不能

让我们用一条通用建议来总结本章。

编写优化编译器是极为困难的。上一届图灵奖颁给了 Alfred Aho 与 Jeffrey Ullman，以表彰他们撰写的一本关于编译器的[千页巨著](https://www.amazon.com/Compilers-Principles-Techniques-Tools-2nd/dp/0321486811/ref=pd_sbs_2?pd_rd_w=UZXK6&pf_rd_p=2419a049-62bf-452e-b0d0-ca5b7e35a7b4&pf_rd_r=AR7FPK4XQJD91HGS4PA3&pd_rd_r=2c8dc8d5-d0b8-40f3-b413-dbc23caaff70&pd_rd_wg=HsK5g&pd_rd_i=0321486811&psc=1)，而这本书还被视为*入门*教科书。

GCC 中包含在 `-O3` 里的优化约有 120 项，其中约 60 项甚至拥有自己的[维基百科页面](https://en.wikipedia.org/wiki/Category:Compiler_optimizations)。在很高的层次上，这些优化通过以下方式提升性能：

- 在寄存器分配、指令调度、死代码消除等基础算法上表现出色；
- 擅长消除不必要的抽象（函数内联、消除临时对象等）；
- 对 CPU 架构了如指掌（在可能时用二进制移位替代除以 2，用 `lea` 替代乘加，总体而言挑选出最优指令）；
- 掌握大量"技巧"（特定的[窥孔优化](https://en.wikipedia.org/wiki/Peephole_optimization)与循环变换），并在有利可图时加以运用。

除非你*真的*热衷于编译器工程，否则我不建议逐条去学。相反，应当逐步建立起对编译器能力的宏观理解。试错在这里通常很有效：只需假定一切足够通用、足够简单的东西都已经被实现了，但始终要去查看汇编输出，以防自己判断失误。

一般而言，当某项优化没有发生时，通常是因为以下三个原因之一：

- 编译器没有足够的信息来断定它将带来收益。
- 该优化实际上并不总是正确：存在某个输入，使得结果与规范不符，即便它在程序员期望的每一个输入上都是正确的。
- 编译器尚未实现它，要么是因为在一般情况下太难实现、计算代价过高，要么是因为过于罕见而不值得费心（例如，为某个特定算法写一个小型库，通常比把它硬编码进编译器更好）。

此外，优化有时仅仅因为源代码过于复杂而失败。

### 检查清单

通常，处理性能的正确思路是：先想清楚实现的主要热点在汇编中应当是什么模样，写出尽可能贴近它的高级代码，然后反复问自己以下问题，直到你对性能感到满意：

0. 编译器是否知道自己被允许做这些优化？（`-O3`、`-march=native`、`-ffast-math`）
1. 是否存在优化版本无法正确工作的边界情况？（使用 `__restrict__` 与 `const` 关键字，尝试 `assume` 技巧）
2. 是否存在某个真实世界的数据集，使得该优化可能并无裨益？（提示、pragma、PGO）
3. 是否至少还有 1000 个其他地方适用此优化？（消除抽象并手动实现，向 GCC 和 Clang 提交特性请求）

在大多数情况下，这些问题的答案中至少有一个会是"否"，然后你就知道该做什么了。
