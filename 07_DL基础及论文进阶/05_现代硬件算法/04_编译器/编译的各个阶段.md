# 编译的各个阶段

在直接跳到编译器优化——这是本章绝大部分内容所讨论的——之前，让我们先简要回顾一下"大局"。略去无聊的部分，把 C 程序变成可执行文件共有 4 个阶段：

1. **预处理（Preprocessing）** 展开宏、从头文件中拉入所包含的源、并从源代码中剥离注释：`gcc -E source.c`（将预处理后的源输出到 stdout）
2. **编译（Compiling）** 解析源、检查语法错误、将其转换为中间表示、执行优化，最终翻译成汇编语言：`gcc -S file.c`（生成 `.s` 文件）
3. **汇编（Assembly）** 把汇编语言转为机器码，只是任何诸如 `printf` 之类的外部函数调用会被替换为占位符：`gcc -c file.c`（生成 `.o` 文件，称为*目标文件*）
4. **链接（Linking）** 最终通过填入实际地址来解析函数调用，并生成可执行二进制文件：`gcc -o binary file.c`

在这些阶段中的每一个，都存在改进程序性能的可能。

### 过程间优化

我们把最后一个[[编译的各个阶段.md|阶段]]即链接放在最后，是因为按文件逐个编译、再把它们链接到一起，既更容易也更快速——这样你可以并行进行，还能缓存中间结果。

这也赋予了以*库*的形式分发代码的能力，库可以是*静态*的，也可以是*共享*的：

- *静态*库只是预编译目标文件的集合，由编译器与其他源合并以生成一个单一的可执行文件，一如平常。
- *动态*库或称*共享*库，是带有额外元信息的预编译可执行文件，说明其可调用位置何在，对这些位置的引用在运行时解析。顾名思义，这允许多个程序之间*共享*已编译的二进制文件。

使用静态库的主要优势在于，你可以执行各类*过程间优化*（interprocedural optimization），它们需要的上下文不止于库函数的签名，例如[[函数与递归.md|函数内联]]或死代码消除。要强制链接器只寻找并接受静态库，可以传入 `-static` 选项。

这一过程称为*链接时优化（link-time optimization，LTO）*，它之所以可行，是因为现代编译器也在目标文件中存储了某种形式的*中间表示*（intermediate representation），使得它们能在整个程序层面执行某些轻量级优化。这也允许在同一个程序中使用不同的编译型语言，只要它们的编译器使用相同的中间表示，甚至能跨越语言边界进行优化。

LTO 是一个相对较新的特性（大约在 2014 年才出现在 GCC 中），而且至今远非完美。在 C 和 C++ 中，确保不因分别编译而损失性能的办法是创建一个*仅含头文件的库*（header-only library）。顾名思义，它们就是包含了所有函数完整定义的头文件，因此只要简单地包含它们，编译器就能获得所有可能的优化。尽管每次你都得从头重新编译库代码，但这种方式保留了充分的控制权，并确保不会损失任何性能。

### 检视输出

检视这些阶段各自的输出，能让你洞察程序内部正在发生什么。

你可以给编译器传入 `-S` 标志，从源代码得到汇编，它会生成一个人类可读的 `*.s` 文件。如果你传入 `-fverbose-asm`，这个文件还会包含关于源代码行号以及所使用变量的一些信息的编译器注释。如果那只是个小片段、而你又懒得动手，可以使用 [Compiler Explorer](https://godbolt.org/)，这是一个非常便捷的在线工具，能把源代码转换为汇编、用颜色高亮逻辑 asm 块、附带一个小型的 x86 指令集参考，并且还提供大量其他编译器、目标平台与语言可供选择。

除汇编之外，另一个最有帮助的抽象层次是编译器在其上执行优化的中间表示。IR 定义了计算本身的流程，并且远不像寄存器数量或特定指令集这类架构特性那样依赖具体平台。检视这些来洞察编译器是如何*看待*你的程序，常常很有用，但这有点超出了本书的范围。

在本章中我们主要使用 [GCC](https://gcc.gnu.org/)，但也会在必要时尽量为 [Clang](https://clang.llvm.org/) 复现示例。这两款编译器在很大程度上彼此兼容，主要只在部分优化标志和细微的语法差异上有所不同。
