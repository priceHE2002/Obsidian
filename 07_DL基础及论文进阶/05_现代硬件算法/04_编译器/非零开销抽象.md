# 非零开销抽象

总的来说，抽象是极好的东西。运用得当，它能减少代码量，减轻程序员的思维负担。

但抽象往往要以性能为代价。当你使用一个共享库时，必须多花几个周期来搬运数据，才能正确地调用其中的函数。当你调用一个虚函数时，你无法可靠地预测接下来要执行的是什么代码，实际上也就承受了一次分支预测失败（branch mispredict）。

诸如 C++ 和 Rust 这类语言大力倡导"零开销"（zero-cost）抽象的理念，即这种抽象没有任何额外的运行时开销，至少在原理上可以被编译器完全消除。但在实践中，并不存在所谓的零开销抽象——编译器技术目前还做不到这一点。

**虚函数（virtual functions）。** 任何类型的运行时多态。

**边界检查（bounds checking）。** 不过编译器很擅长消除它们。

**广义上任何复杂的代码。** 这里有一个我个人颇为在意的例子：C++ 标准库中的 `std::min`。它的表现经常比手动取最小值还要差，原因在于它的实现并不只是 `return (a < b ? a : b)`，而是为了通用性使用了可变参数初始化列表（variadic initializer lists）和迭代器：

```cpp
template<typename _Tp> GLIBCXX14_CONSTEXPR inline _Tp min(initializer_list<_Tp> __l) {
    return *std::min_element(__l.begin(), __l.end());
}
```

通常，把一个小程序改写得更直白、更贴近硬件并不算太难。如果你开始一层层地剥去抽象，编译器最终就会让步。

面向对象语言，尤其是函数式语言，往往带有一些极难穿透的此类抽象。正因如此，人们在编写性能敏感的软件（解释器、运行时、数据库）时，常常倾向于采用更接近 C 的风格，而非更高级的语言。

蓄着浓密胡须的 C / 汇编程序员。

### 内存

指针追踪（pointer chasing）。

```c++
typedef vector< vector<int> > matrix;
matrix a(n, vector<int>(n, 0));

int val = a[i][j];
```

这种方式慢了将近一倍：你需要先取出

```c++
int a = new int[n * n];
memset(a, 0, 4 * n* n);

int val = a[i * n + j];
```

如果你确实想要一个抽象层，可以写一个包装：

```c++
template<typename T>
struct Matrix {
    int x, y, n, N;
    T* data;
    T* operator[](int i) { return data + (x + i) * N + y; }
};
```

例如，[[缓存无关算法.md|缓存无关转置]]会是这样的：

```c++
Matrix<T> subset(int _x, int _y, int _n) { return {_n, _x, _y, N, data}; }

Matrix<T> transpose() {
    if (n <= 32) {
        for (int i = 0; i < n; i++)
            for (int j = 0; j < i; j++)
                swap((*this)[j][i], (*this)[i][j]);
    } else {
        auto A = subset(x, y, n / 2).transpose();
        auto B = subset(x + n / 2, y, n / 2).transpose();
        auto C = subset(x, y + n / 2, n / 2).transpose();
        auto D = subset(x + n / 2, y + n / 2, n / 2).transpose();
        for (int i = 0; i < n; i++)
            for (int j = 0; j < n; j++)
                swap(B[i][j], C[i][j]);
    }

    return *this;
}
```

我个人更倾向于编写底层代码，因为它更容易优化。

它更干净？我不这么认为。
