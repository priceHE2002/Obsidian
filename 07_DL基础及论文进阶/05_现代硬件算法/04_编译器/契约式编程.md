# 契约式编程

在 Java 和 Rust 这类"安全"语言中，你通常对每一种可能的操作和每一种可能的输入都有明确的行为定义。也有一些内容是"欠定义"（under-defined）的，例如哈希表中键的顺序或 `std::vector` 的增长因子，但这些通常是一些细枝末节，留给具体实现去决定，以便在未来获得潜在的性能提升。

相比之下，C 和 C++ 把未定义行为（undefined behavior）的概念推向了另一个极端。某些操作在编译或运行时都不会引发错误，却根本就是"不被允许"的——其含义是，程序员与编译器之间存在着一份"契约"：一旦发生未定义行为，编译器在法理上可以为所欲为，包括炸掉你的显示器或格式化你的硬盘。但编译器工程师对做这些事并无兴趣。相反，未定义行为被用来保证不存在边界情况（corner case），并辅助优化。

### 未定义行为为何存在

导致未定义行为的操作主要有两大类：

- 几乎可以肯定属于无意 bug 的操作，例如除以零、解引用空指针，或从未初始化的内存中读取。你希望能在测试时尽快捕获它们，因此崩溃或产生某种非确定性行为，反而比让它们始终执行某个固定的回退动作（比如返回零）更好。

  你可以借助*消毒剂*（sanitizers）编译并运行程序，以便在早期捕获未定义行为。在 GCC 和 Clang 中，可以使用 `-fsanitize=undefined` 标志，那些以引发 UB 而臭名昭著的操作会被插桩以在运行时检测它。

- 在不同平台上可观察行为略有差异的操作。例如，把一个整数左移超过 31 位的结果是未定义的，因为执行该操作的指令在 Arm 与 x86 CPU 上的实现方式不同。如果你把某一种特定行为标准化，那么为另一平台编译的所有程序就不得不多花几个周期来检查这个边界情况，因此最好将其留作未定义。

  有时，当某种平台相关行为确有正当用途时，与其将其声明为未定义，不如留作*实现定义*（implementation-defined）。例如，右移一个[[整数.md|负整数]]的结果取决于平台：它可能补零，也可能补一（例如，把 `11010110 = -42` 右移一位，结果既可能是 `01101011 = 107`，也可能是 `11101011 = -21`，两种用途都合情合理）。

将某事物定为未定义而非实现定义，同样有助于编译器的优化。考虑有符号整数溢出的情形。在几乎所有体系结构上，[[整数.md|有符号整数]]的溢出方式都与无符号整数相同，即 `INT_MAX + 1 == INT_MIN`，然而根据 C++ 标准，这却是未定义行为。这完全是有意为之：如果你禁止有符号整数溢出，那么 `(x + 1) > x` 对 `int` 就保证恒为真，但对 `unsigned int` 却不然，因为 `(x + 1)` 可能溢出。对于有符号类型，这让编译器可以把这类检查优化掉。

一个更自然的例子，是考虑带有整数控制变量的循环。现代 C++ 以及 Rust 这类语言鼓励程序员使用无符号整数（`size_t` / `usize`），而 C 程序员却固执地坚持使用 `int`。要理解其中缘由，请看下面这个 `for` 循环：

```cpp
for (unsigned int i = 0; i < n; i++) {
    // ...
}
```

这个循环执行多少次？从技术上讲有两个合法答案：$n$ 与无穷大。后者出现在 $n$ 超过 $2^{32}$、使得 $i$ 每 $2^{32}$ 次迭代就重置为零的情况。虽然前者大概是程序员所假设的，但为了符合语言规范，编译器仍须插入额外的运行时检查，并把两种情况区别对待、采用不同的优化。与此同时，`int` 版本会恰好执行 $n$ 次迭代，因为符号溢出的可能性在定义上就被排除了。

### 消除边界情况

"安全"的编程风格通常包含大量运行时检查，但它们未必要以性能为代价。

例如，Rust 在索引数组及其他随机访问结构时会著名地使用边界检查。在 C++ 标准库中，`vector` 和 `array` 既有"不安全"的 `[]` 运算符，也有"安全"的 `.at()` 方法，大致如下：

```cpp
T at(size_t k) {
    if (k >= size())
        throw std::out_of_range("Array index exceeds its size");
    return _memory[k];
}
```

有趣的是，这些检查在运行时极少真正执行，因为编译器常常能在编译期证明每次访问都会落在边界之内。例如，在一个从 1 到数组大小、且在每一步都索引第 $i$ 个元素的 `for` 循环中，不可能发生任何非法之事，因此边界检查可以被安全地优化掉。

### 假设

当编译器无法证明边界情况不存在，而*你*能够证实时，就可以通过未定义行为这一机制来提供这份额外的信息。

Clang 提供了一个有用的 `__builtin_assume` 函数，你可以在其中放入一个保证为真的语句，编译器就会在优化时利用这一假设。在 GCC 中，可以用 `__builtin_unreachable` 做到同样的事：

```cpp
void assume(bool pred) {
    if (!pred)
        __builtin_unreachable();
}
```

例如，你可以在上面示例的 `at` 之前放上 `assume(k < vector.size())`，如此边界检查便会被优化掉。

把它与 `assert` 和 `static_assert` 结合使用来查找 bug 也相当有用：同样的函数既可以在调试版本中用于检查前置条件，又可以在生产版本中用来提升性能。

### 算术

边界情况是你应当牢记在心的，尤其在优化算术时。

对于[[浮点数.md|浮点运算]]，这较少成为顾虑，因为你只需用 `-ffast-math` 标志（它也包含在 `-Ofast` 中）关闭严格的规范兼容性即可。你几乎不得不这么做，否则编译器除了按源代码中的顺序、不做任何优化地执行算术运算之外别无他法。

对于整数运算则不同，因为结果必须始终精确。考虑除以 2 的情形：

```cpp
unsigned div_unsigned(unsigned x) {
    return x / 2;
}
```

一个广为人知的优化是用一次右移（`x >> 1`）来替代：

```nasm
shr eax
```

对于所有*正*数，这显然是正确的，但一般情形又如何呢？

```cpp
int div_signed(int x) {
    return x / 2;
}
```

如果 `x` 是负数，简单地移位就不奏效——无论移入的是零还是符号位：

- 如果移入零，我们会得到一个非负的结果（符号位为零）。
- 如果移入符号位，那么舍入将朝向负无穷而非零（`-5 / 2` 会等于 `-3` 而非 `-2`）[^python]。

[^python]: 趣闻：在 Python 中，对负数做整数除法出于某种原因会向下取整，因此 `-5 // 2 = -3`，且等价于 `-5 >> 1 = -3`。我怀疑 Guido van Rossum 当初设计这门语言时脑子里想着这个优化，但理论上，一个包含大量除以二运算的[[编程语言.md#托管语言|JIT 编译]]的 Python 程序，可能比功能类似的 C++ 程序更快。

因此，对于一般情形，我们必须插入一些"拐杖"才能使其成立：

```nasm
mov  ebx, eax
shr  ebx, 31    ; extract the sign bit
add  eax, ebx   ; add 1 to the value if it is negative to ensure rounding towards zero
sar  eax        ; this one shifts in sign bits
```

当本意只是正数情形时，我们也可以利用 `assume` 机制来排除 `x` 为负的可能性，从而免去过问这个边界情况：

```cpp
int div_assume(int x) {
    assume(x >= 0);
    return x / 2;
}
```

尽管在这种特定情形下，表达"我们只期望非负数"的最佳语法或许是直接采用无符号整数类型。

由于诸如此类的细微差别，把中间函数中的代数展开、并亲手化简算术，往往比依赖编译器去做更有好处。

### 内存别名

编译器在优化涉及内存读写操作时表现相当糟糕。这是因为它们常常没有足够的上下文来保证优化的正确性。

考虑下面的例子：

```c++
void add(int *a, int *b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

由于这个循环的每次迭代相互独立，它可以被并行执行并[[SIMD并行.md|向量化]]。但从技术上讲，真的可以吗？

如果数组 `a` 与 `b` 存在交集，就可能出现问题。考虑 `b == a + 1` 的情形，也就是说，`b` 只是 `a` 从第二个元素开始的视图。在这种情况下，下一次迭代依赖于前一次，唯一正确的解法是顺序执行循环。即便程序员明知这种情况不可能发生，编译器也不得不去检查这类可能性。

这正是我们需要 `const` 与 `restrict` 关键字的原因。前者强制保证我们不会通过该指针变量修改内存，后者则是向编译器声明这块内存保证不会被取别名（aliased）。

```cpp
void add(int * __restrict__ a, const int * __restrict__ b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

这些关键字本身也是用于自文档化的好主意。

### C++ 契约

契约式编程是一项未被充分利用却极为强大的技术。

有一份后期提案，准备以[契约属性](http://www.hellenico.gr/cpp/w/cpp/language/attributes/contract.html)的形式把契约式设计加入 C++ 标准，其功能等价于我们手写的、依赖特定编译器的 `assume`：

```c++
T at(size_t k) [[ expects: k < n ]] {
    return _memory[k];
}
```

这类属性有 3 种类型——`expects`、`ensures` 与 `assert`——分别用于在函数中指定前置与后置条件，以及放在程序中任意位置的一般性断言。

遗憾的是，这一激动人心的新特性[尚未最终标准化](https://www.reddit.com/r/cpp/comments/cmk7ek/what_happened_to_c20_contracts/)，更遑论在主流 C++ 编译器中实现。但也许再过几年，我们就能写出这样的代码：

```c++
bool is_power_of_two(int m) {
    return m > 0 && (m & (m - 1) == 0);
}

int mod_power_of_two(int x, int m)
    [[ expects: x >= 0 ]]
    [[ expects: is_power_of_two(m) ]]
    [[ ensures r: r >= 0 && r < m ]]
{
    int r = x & (m - 1);
    [[ assert: r = x % m ]];
    return r;
}
```

某些形式的契约式编程在其他面向性能的语言中也有提供，例如 [Rust](https://docs.rs/contracts/latest/contracts/) 与 [D](https://dlang.org/spec/contracts.html)。

一条通用且语言无关的建议是：随时[[编译的各个阶段.md|查看编译器生成的汇编]]，如果它并非你所期望的那样，就试着去想那些可能限制了编译器优化的边界情况。
