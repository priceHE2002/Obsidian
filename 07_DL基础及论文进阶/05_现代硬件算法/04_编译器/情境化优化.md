# 情境化优化

<!--

Generally, you always want to specify the exact platform you are running and turn on `-O3`, but other optimizations, like the ones discussed [in the previous section](../assembly), are far more situational and require some input from the programmer.

-->

`-O2` 和 `-O3` 启用的大多数编译器优化，都保证能提升性能或至少不会严重损害性能。那些未被包含在 `-O3` 中的优化，要么并非严格符合规范，要么极度依赖具体情境，需要程序员提供一些额外输入来帮助决定是否值得使用。

让我们讨论一下最常用、且本书此前也已涵盖的那些优化。

### 循环展开

[[循环与条件分支.md#跳转|循环展开]]默认是关闭的，除非循环执行一个编译期已知的、较小的常数次迭代——此时它会被替换为一段完全没有跳转、重复排列的指令序列。可以用 `-funroll-loops` 标志全局启用，它会展开所有迭代次数可在编译期或进入循环时确定的循环。

你也可以用一个 pragma 针对特定循环：

```c++
#pragma GCC unroll 4
for (int i = 0; i < n; i++) {
    // ...
}
```

循环展开会让二进制文件变大，而且可能让它变快，也可能不会。不要狂热地使用它。

### 函数内联

[[函数与递归.md#调用约定|内联]]最好交由编译器决定，但你可以用 `inline` 关键字来影响它：

```c++
inline int square(int x) {
    return x * x;
}
```

不过，如果编译器认为潜在的性能收益不值一提，这个提示可能会被忽略。你可以通过加上 `always_inline` 属性来强制内联：

```c++
#define FORCE_INLINE inline __attribute__((always_inline))
```

还有一个 `-finline-limit=n` 选项，可以让你为内联函数的大小（以指令数为单位）设置一个特定阈值。它在 Clang 中的等价物是 `-inline-threshold`。

### 分支的可能性

[[机器码布局.md#指令缓存|分支的可能性]]可以通过 `if` 与 `switch` 中的 `[[likely]]` 与 `[[unlikely]]` 属性来提示：

```c++
int factorial(int n) {
    if (n > 1) [[likely]]
        return n * factorial(n - 1);
    else [[unlikely]]
        return 1;
}
```

这是 C++20 才出现的新特性。在此之前，有各编译器特定的内建函数，以类似方式用于包裹条件表达式。旧版 GCC 中的同一例子：

```c++
int factorial(int n) {
    if (__builtin_expect(n > 1, 1))
        return n * factorial(n - 1);
    else
        return 1;
}
```

<!--
What it usually does is it swaps the branches so that the more likely one goes immediately after jump (recall that "don't jump" branch is taken by default). The performance gain is usually rather small, because for most hot spots hardware branch prediction works just fine.
-->

还有许多类似的、需要你为编译器指明方向的情形，但我们会在它们变得更相关时再展开。

### 基于性能剖析的优化

把所有这类元数据加到源代码上是件苦差事。即便没有这一步，人们已经讨厌写 C++ 了。

某项优化是否有益，也并不总是显而易见。要为分支重排、函数内联或循环展开做决策，我们需要回答如下这类问题：

- 这个分支被执行的频率有多高？
- 这个函数被调用的频率有多高？
- 这个循环的平均迭代次数是多少？

对我们而言幸运的是，有一种方法可以自动提供这些真实世界的信息。

*基于性能剖析的优化*（Profile-guided optimization，PGO，又称"pogo"，因为这样叫更轻松也更有趣）是一种利用[[性能剖析.md|剖析数据]]把性能提升到仅凭静态分析所不及的技术。简而言之，它包括在程序中的关注点插入计时器与计数器，在真实数据上编译并运行它，然后再编译一次，但这次提供来自测试运行的额外信息。

整个流程由现代编译器自动完成。例如，`-fprofile-generate` 标志会让 GCC 用剖析代码插桩程序：

```
g++ -fprofile-generate [other flags] source.cc -o binary
```

在我们运行程序之后——最好是在尽可能贴近真实用例的输入上——它会生成一堆 `*.gcda` 文件，其中包含测试运行的日志数据，此后我们便可以重新构建程序，但这次加上 `-fprofile-use` 标志：

```
g++ -fprofile-use [other flags] source.cc -o binary
```

它通常能为大型代码库带来 10–20% 的性能提升，正因如此，它常被纳入性能敏感项目的构建流程。这也更说明投资于扎实的基准测试代码是值得的。
