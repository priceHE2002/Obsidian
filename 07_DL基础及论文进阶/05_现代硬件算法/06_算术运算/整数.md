# 整数

如果你是从头开始按序阅读本章，你可能会纳闷：为什么我要在浮点之后才介绍整数运算？它难道不是应该更简单吗？

确实：普通的整数表示更简单。但反直觉的是，正是这种简单性允许了更多"用一种运算表达另一种运算"的可能性。而浮点表示是如此笨拙，以至于它们的多数运算都由硬件实现；高效地操作整数则需要更有创造性地运用指令集。

## 二进制格式

*无符号整数*（unsigned integers）就是写成二进制的自然数：

$$
\begin{aligned}
   5_{10}   &= 101_2 = 4 + 1
\\ 42_{10}  &= 101010_2 = 32 + 8 + 2
\\ 256_{10} &= 100000000_2 = 2^8
\end{aligned}
$$

当运算结果无法容纳于字长时（例如，对于 32 位无符号整数，结果大于等于 $2^{32}$），它会发生*溢出*（overflow），仅保留结果的最低 32 位。类似地，如果结果是负值，它会*下溢*（underflow），将其加到 $2^{32}$ 上，从而始终停留在 $[0, 2^{32})$ 范围内。

这等价于对所有运算在模 2 的幂下进行：

$$
\begin{aligned}
    256                 &\equiv 0 \pmod {2^8}
\\  2021                &\equiv 229 \pmod {2^8}
\\  -42 \equiv 256 - 42 &\equiv 214 \pmod {2^8}
\end{aligned}
$$

无论哪种情况，都会置位一个特殊的标志，你可以对其进行检查，但通常当人们显式使用无符号整数时，他们正预期这种行为。

### 有符号整数

*有符号整数*（signed integers）通过专门用最高位表示数字的符号来支持存储负值，方式与浮点数类似。这将有符号非负数的表示范围减半：现在 32 位整数的最大可能值是 $(2^{31}-1)$ 而非 $(2^{32}-1)$。但负值的编码与浮点数并不完全相同。

计算机工程师甚至比程序员更懒——这不仅仅受简化直觉的驱使，也为了节省晶体管面积。这可以通过复用你已有的、用于其他运算的电路来实现，而他们在设计有符号整数格式时正是以此为目标：

- 对于 $n$ 位有符号整数类型，$[0, 2^{n-1})$ 范围内的所有数字的编码与其无符号二进制表示保持不变。
- $[-2^{n-1}, 0)$ 范围内的所有数字按序编码在"正数"范围之后——即从代码为 $(2^{n-1})$ 的 $(-2^{n - 1})$ 开始，到代码为 $(2^n - 1)$ 的 $(-1)$ 结束。

一种看待此问题的方式是：所有负数都仿佛是从 $2^n$ 中减去后再编码——这一运算被称为 *补码*（two's complement）：

$$
\begin{aligned}
-x &= 2^{32} - x
\\ &= \bar{x} + 1
\end{aligned}
$$

这里 $\bar{x}$ 表示按位取反（bitwise negation），也可以理解为从 $(2^n - 1)$ 中减去 $x$。

作为练习，下面是关于有符号整数的一些事实：

- 所有正数和零与其二进制记法保持一致。
- 所有负数最高位被置一。
- 负数比正数更多（恰好多一个——因为零的存在）。
- 对于 `int`，如果向 $(2^{31}-1)$ 加 $1$，结果将是 $-2^{31}$，表示为 `10000000`（出于讲解目的，我们只写 8 位而非 32 位）。
- 已知正数 `x` 的二进制记法，可以得到 `-x` 的二进制记法为 `~x + 1`。
- `-1` 表示为 `~1 + 1 = 11111110 + 00000001 = 11111111`。
- `-42` 表示为 `~42 + 1 = 11010101 + 00000001 = 11010110`。
- 数字 `-1 = 11111111` 之后是 `0 = -1 + 1 = 11111111 + 00000001 = 00000000`。

这种编码的主要优势在于，你无需做任何事就能将无符号整数转换为有符号整数（可能只需检查溢出），并且你可以为大多数运算复用同一套电路，或许只需要在比较等操作中翻转符号位。

话虽如此，你需要对有符号整数溢出保持谨慎。尽管它们几乎总是与无符号整数以相同方式溢出，编程语言通常将溢出的可能性视为未定义行为（undefined behavior）。如果你需要对整数变量进行溢出，请将它们转换为无符号整数：这反正是免费的。

### 整数类型

整数有不同大小，但功能大致相同。

| 位数 | 字节数 | 有符号 C 类型         | 无符号 C 类型        | 汇编名 |
|-----:|-------|----------------------|----------------------|----------|
|    8 | 1     | `signed char`[^char] | `unsigned char`      | `byte`   |
|   16 | 2     | `short`              | `unsigned short`     | `word`   |
|   32 | 4     | `int`                | `unsigned int`       | `dword`  |
|   64 | 8     | `long long`          | `unsigned long long` | `qword`  |

[^char]: 注意 `char`、`unsigned char` 与 `signed char` 在技术上是三种不同的类型。C 标准将普通 `char` 究竟是有符号还是无符号留给具体实现决定（在大多数编译器上，它是有符号的）。

整数的各个位只是顺序存储。这里唯一的歧义是以何种顺序存储它们——从左到右还是从右到左——称为 *字节序*（endianness）。根据体系结构的不同，格式可以是：

- *小端序*（little-endian），先列出*较低*的位。例如，$42_{10}$ 将被存储为 $010101$。
- *大端序*（big-endian），先列出*较高*的位。本文之前所有的例子都遵循它。

这看似是一个重要的体系结构方面，但在大多数情况下并无差别：只需选定一种风格并坚持即可。但在某些情况下它确实有影响：

- 小端序的优势在于，你可以通过将值转换为更小的类型（例如 `long long` 转 `int`）来只加载更少的字节，这在大多数情况下意味着什么都不做——得益于*寄存器别名*（register aliasing），`eax` 指代 `rax` 的前 4 个字节，因此转换本质上是免费的。它也更容易以各种类型大小读取数值——而在大端序体系结构上，从 `long long` 数组加载一个 `int` 需要将指针偏移 2 个字节。
- 大端序的优势在于先加载较高字节，理论上可以使从高位到低位的例程（如比较和打印）更快。你也可以执行某些检查，例如仅通过加载其第一个字节来判断一个数是否为负。

大端序也更"自然"——这正是我们在纸上书写二进制数的方式——但拥有更快类型转换的优势压倒了它。因此，小端序在大多数硬件上被默认使用，尽管某些 CPU 是"双端序"（bi-endian）的，可以按需配置以切换模式。

### 128 位整数

有时我们需要将两个 64 位整数相乘以得到一个 128 位整数——通常用作临时值，并立即对 64 位整数取模。

没有 128 位寄存器来保存这种乘法的结果，因此 `mul` 指令除了正常的 `mul r r` 形式（将寄存器中的值相乘并保留结果的后半部分）外，还有另一种 `mul r` 模式：它将存储在 `rax` 寄存器中的任何值与其操作数相乘，并将结果写入两个寄存器——结果的低 64 位进入 `rax`，高 64 位进入 `rdx`：

```nasm
; input: 64-bit integers a and b, stored in rsi and rdi
; output: 128-bit product a * b, stored in rax (lower 64-bit) and rdx (higher 64-bit)
mov     rax, rdi
mov     r8, rdx
imul    rsi
```

某些编译器有一个支持这一运算的独立类型。在 GCC 和 Clang 中，它以 `__int128` 提供：

```cpp
void prod(int64_t a, int64_t b, __int128 *c) {
    *c = a * (__int128) b;
}
```

其典型用途是立即提取乘法结果的低部分或高部分，然后不再理会：

```c++
__int128_t x = 1;
int64_t hi = x >> 64;
int64_t lo = (int64_t) x; // will be just truncated
```

除了乘法之外的所有用途，128 位整数只是被捆绑为两个寄存器。这使得拥有一个完备的 128 位类型显得过于怪异，因此对其支持是有限的，仅限于基本算术运算。例如：

```c++
__int128_t add(__int128_t a, __int128_t b) {
    return a + b;
}
```

会被编译为：

```nasm
add:
    mov rax, rdi
    add rax, rdx    ; this sets the carry flag in case of an overflow
    adc rsi, rcx    ; +1 if the carry flag is set
    mov rdx, rsi
    ret
```

其他平台也提供类似机制来处理长于字长的乘法。例如，Arm 有 `mulhi` 和 `mullo` 指令，分别返回乘法的低部分和高部分，而 x86 的 [[SIMD并行.md|SIMD 扩展]] 也有类似的 32 位指令。
