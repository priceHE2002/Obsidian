# 如何获得准确结果

时常会出现这样的情况：存在两个库算法实现，各自维护着自己的基准测试代码，并各自声称比对方更快。这让所有相关方都感到困惑，尤其是用户，他们不得不在两者间做出某种选择。

此类情形通常并非由其作者的欺诈行为引起；他们只是对"更快"的定义不同，而事实上，仅定义和使用单一性能指标往往就问题重重。

### 测量正确的对象

有许多因素会给基准测试引入偏差。

**不同的数据集。** 有许多算法的性能在某种程度上取决于数据集的分布。为了定义，例如，最快的排序、最短路径或二分查找算法是什么，你必须固定算法所运行的数据集。

这一点有时甚至适用于处理单个输入的算法。例如，给 GCD 实现喂入顺序数字不是个好主意，因为这会让分支变得非常可预测：

```c++
// 不要这样做
int checksum = 0;

for (int a = 0; a < 1000; a++)
    for (int b = 0; b < 1000; b++)
        checksum ^= gcd(a, b);
```

然而，如果我们随机地采样这些相同的数字，分支预测会变得困难得多，基准测试耗时也更长，尽管它处理的是相同的输入，只是顺序改变了：

```c++
int a[1000], b[1000];

for (int i = 0; i < 1000; i++)
    a[i] = rand() % 1000, b[i] = rand() % 1000;

int checksum = 0;

for (int t = 0; t < 1000; t++)
    for (int i = 0; i < 1000; i++)
        checksum += gcd(a[i], b[i]);
```


尽管对大多数情况而言最合理的选择是简单地均匀随机采样，但许多真实世界应用的数据分布远非均匀，所以你无法只选一种。一般而言，一个好的基准测试应当是特定于应用的，并使用尽可能代表你真实使用场景的数据集。

**多目标。** 一些算法设计问题不止一个关键目标。例如，哈希表除了高度依赖键的分布外，还需仔细权衡：

- 内存占用，
- 添加查询的延迟，
- 成员查询命中的延迟，
- 成员查询未命中的延迟。

在哈希表实现之间做选择的唯一方法，是把多个变体放入应用中实际尝试。

**延迟 vs 吞吐。** 人们常常忽略的另一个方面是，即使对单个查询而言，执行时间也可以有多种定义方式。

当你写出这样的代码时：

```c++
for (int i = 0; i < N; i++)
    q[i] = rand();

int checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

然后对整体计时并除以迭代次数，你实际上测量的是查询的*吞吐（throughput）*——它每单位时间能处理多少操作。这通常小于单独处理一个操作实际所需的时间，因为存在交错执行。

要测量实际的*延迟（latency）*，你需要在各次调用之间引入依赖：

```c++
for (int i = 0; i < N; i++)
    checksum ^= lower_bound(checksum ^ q[i]);
```

这在存在流水线停顿问题的算法中通常差异最大，例如比较有分支算法与无分支算法时。

**冷缓存（Cold cache）。** 另一个偏差来源是*冷缓存效应*，即内存读取最初耗时更长，因为所需数据尚未进入缓存。

这可通过在开始测量前进行一次*预热运行（warm-up run）*来解决：

```c++
// 预热运行

volatile checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);


// 实际运行

clock_t start = clock();
checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

如果答案验证比计算某个校验和更复杂，有时将预热运行与答案验证结合起来也很方便。

**过度优化（Over-optimization）。** 有时基准测试完全错误，是因为编译器干脆把被测试的代码优化掉了。为防止编译器偷工减料，你需要添加校验和，并将其打印到某处或加上 `volatile` 修饰符，后者还能防止循环迭代的任何形式交错。

对于只写数据的算法，你可以使用 `__sync_synchronize()` 内建函数添加内存屏障，防止编译器累积更新。

### 降低噪声

-->

我们描述过的问题会产生测量中的*偏差（bias）*：它们持续地让某个算法优于另一个。还有另一类可能的问题会导致不可预测的偏移或完全随机的噪声，从而增加*方差（variance）*。

这类问题由副作用和某种外部噪声引起，主要源于"吵闹的邻居（noisy neighbors）"和 CPU 频率调节（frequency scaling）：

- 如果你基准测试一个计算密集型算法，请用 `perf stat` 以周期为单位测量其性能：这样它将与时钟频率无关，而时钟频率的波动通常正是噪声的主要来源。
- 否则，将核心频率设为你的预期值，并确保没有任何东西干扰它。在 Linux 上你可以用 `cpupower` 完成（例如，`sudo cpupower frequency-set -g powersave` 将其设为最低，或 `sudo cpupower frequency-set -g ondemand` 启用睿频加速）。我使用一个 [方便的 GNOME shell 扩展](https://extensions.gnome.org/extension/1082/cpufreq/)，它有一个单独的按钮来做这件事。
- 在适用时，关闭超线程并把任务绑定到特定核心。确保系统上没有其它任务在运行，关闭网络，并尽量不要动鼠标。

你无法完全消除噪声和偏差。甚至程序的名字都可能影响其速度：可执行文件的名字最终会出现在一个环境变量中，环境变量最终落到调用栈上，因此名字的长度会影响栈对齐，而这可能导致因跨越缓存行或内存页边界而使数据访问变慢。

在指导优化、尤其是向他人汇报结果时，考虑噪声很重要。除非你预期的是 2 倍量级的改进，否则要把所有微基准测试当作 A/B 测试一样对待。

当你在笔记本电脑上运行一个不足一秒的程序时，±5% 的性能波动完全正常。因此，如果你想决定是回退还是保留一个潜在的 +1% 改进，就一直运行直到达到统计显著性，你可以通过计算方差和 p 值来确定它。
