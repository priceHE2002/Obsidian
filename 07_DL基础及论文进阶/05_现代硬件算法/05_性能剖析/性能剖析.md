# 性能剖析

盯着源代码或其汇编代码，是一种流行但并非最有效的排查性能问题的方法。当性能达不到预期时，使用一类统称为*剖析器（profilers）*的专用程序分析工具，往往能更快地定位根本原因。

剖析器种类繁多。我倾向于用物理学家和其他自然科学家研究微小事物时的类比来理解它们——依据所需的精度水平选择合适的工具：

- 当对象处于微米尺度时，他们使用光学显微镜。
- 当对象处于纳米尺度、光不再与之发生作用时，他们使用电子显微镜。
- 当对象比这更小（例如原子内部）时，他们转而依赖关于事物如何运转的理论与假设（并通过复杂而间接的实验来验证这些假设）。

类似地，有三种主要的剖析技术，各自遵循不同的原理，适用领域不同，可达到的精度水平也不同：

- [[插桩.md|插桩（Instrumentation）]] 让你能够测量整个程序或其中某部分的耗时，并统计你所关注的特定事件。
- [[统计采样剖析.md|统计采样剖析（Statistical profiling）]] 让你深入到汇编层面，跟踪各类对性能至关重要的*硬件事件（hardware events）*，例如分支预测失败或缓存未命中。
- [[机器码分析器.md|程序模拟（Program simulation）]] 让你深入到单个周期层面，查看 CPU 在执行一小段汇编代码片段时，每个周期内部正在发生什么。

实际的算法设计在很大程度上也可被视为一门经验科学。我们大量依赖相同的实验方法，不过这并不是因为我们不知道某些自然界的根本奥秘，而主要是因为现代计算机过于复杂而难以分析——此外，由于我们这些普通软件工程师因硬件公司的知识产权保护而无法了解某些细节，这一点同样成立（事实上，考虑到最准确的 x86 指令表是[逆向工程](https://arxiv.org/pdf/1810.04610.pdf)得来的，有理由相信 Intel 自己也不清楚这些细节）。

在本章中，我们将研究这三种关键的剖析方法，以及一些历经时间考验、用于管理涉及性能评估的计算实验的实践经验。
