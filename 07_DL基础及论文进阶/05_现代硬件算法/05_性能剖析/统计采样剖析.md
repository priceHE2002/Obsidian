# 统计采样剖析

[[插桩.md|插桩（Instrumentation）]] 是一种相当繁琐的剖析方式，尤其是当你关注程序的多个细小片段时。即便它能由工具部分自动化，它仍然因其固有的开销而无法帮助你收集某些细粒度的统计信息。

另一种侵入性更小的剖析方法，是在随机间隔打断程序的执行，并查看指令指针（instruction pointer）停在哪里。指针在每个函数代码块中停下来的次数，将大致正比于执行这些函数所耗费的总时间。你还能通过这种方式获得其他一些有用信息，例如通过检查 [[函数与递归.md|调用栈（call stack）]] 来找出哪些函数被哪些函数调用。

原则上，这只需用 `gdb` 运行一个程序并在随机间隔按 `ctrl+c` 即可完成，但现代 CPU 和操作系统为此类剖析提供了专门的工具。

### 硬件事件

硬件*性能计数器（performance counters）*是微处理器内部内置的特殊寄存器，可以存储某些与硬件相关活动的计数。它们在微芯片上添加起来很廉价，因为它们本质上只是带有激活连线的二进制计数器。

每个性能计数器都连接到电路的一个很大子集，并可被配置为在特定硬件事件（例如一次分支预测失败或一次缓存未命中）发生时递增。你可以在程序开始时重置某个计数器，运行程序，并在结束时输出其存储的值，该值将等于整个执行过程中某一事件被触发的确切次数。

你也可以通过多路复用（multiplexing）来跟踪多个事件，即在均匀间隔处暂停程序并重新配置计数器。这种情况下结果并不精确，而是统计意义上的近似。这里的一个微妙之处在于：其准确性无法通过简单地提高采样频率来改善，因为那会过度影响性能、从而扭曲分布，所以为了收集多项统计信息，你需要让程序运行更长的时间。

总体而言，事件驱动的统计采样剖析通常是最有效、最简便的诊断性能问题的方法。

### 使用 perf 进行剖析

依赖上述事件采样技术的性能分析工具被称为*统计剖析器（statistical profilers）*。这类工具很多，但本书主要使用的是 [perf](https://perf.wiki.kernel.org/)，它是随 Linux 内核发布的统计剖析器。在非 Linux 系统上，你可以使用 Intel 的 [VTune](https://software.intel.com/content/www/us/en/develop/tools/oneapi/components/vtune-profiler.html#gs.cuc0ks)，它提供大致相同的功能。它是免费的，尽管属于专有软件，且你需要每 90 天刷新一次社区许可证，而 perf 是自由软件意义上的免费。

Perf 是一个命令行应用程序，基于程序的实时执行生成报告。它不需要源代码，且能剖析范围极广的应用程序，甚至是那些涉及多进程并与操作系统交互的程序。

为便于说明，我编写了一个小程序，它创建一个包含一百万个随机整数的数组、对其排序，然后在上面进行一百万次二分查找：

```c++
void setup() {
    for (int i = 0; i < n; i++)
        a[i] = rand();
    std::sort(a, a + n);
}

int query() {
    int checksum = 0;
    for (int i = 0; i < n; i++) {
        int idx = std::lower_bound(a, a + n, rand()) - a;
        checksum += idx;
    }
    return checksum;
}
```

在编译它（`g++ -O3 -march=native example.cc -o run`）之后，我们可以用 `perf stat ./run` 运行它，该程序会输出执行期间基础性能事件的计数：

你可以看到，执行耗时 0.53 秒（或在 1.32 GHz 有效时钟频率下为 852M 个周期），期间执行了 479M 条指令。还存在 122.7M 次分支，其中 15.7% 被预测失败。

你可以用 `perf list` 获取所有受支持事件的列表，然后用 `-e` 选项指定你想要的特定事件列表。例如，为诊断二分查找，我们主要关心缓存未命中：

```yaml
> perf stat -e cache-references,cache-misses ./run

91,002,054      cache-references:u                                          
44,991,746      cache-misses:u      # 49.440 % of all cache refs
```

就其本身而言，`perf stat` 只是为整个程序设置性能计数器。它能告诉你分支预测失败的总次数，却无法告诉你它们*发生在哪里*，更不用说*为什么*发生。

要尝试我们之前讨论过的"冻结整个世界（stop-the-world）"方法，我们需要使用 `perf record <cmd>`，它记录剖析数据并将其转储为 `perf.data` 文件，然后调用 `perf report` 来检查它。我强烈建议你亲自去试一试，因为最后一个命令是交互式且彩色的，但对于现在无法操作的人，我会尽力描述。

当你调用 `perf report` 时，它首先显示一个类似 `top` 的交互式报告，告诉你哪些函数占用了多少时间：

```
Overhead  Command  Shared Object        Symbol
  63.08%  run      run                  [.] query
  24.98%  run      run                  [.] std::__introsort_loop<...>
   5.02%  run      libc-2.33.so         [.] __random
   3.43%  run      run                  [.] setup
   1.95%  run      libc-2.33.so         [.] __random_r
   0.80%  run      libc-2.33.so         [.] rand
```

注意，对于每个函数，列出的是其*开销（overhead）*而非总运行时间（例如，`setup` 包含了 `std::__introsort_loop`，但只有它自身的开销被记为 3.43%）。有一些工具可以根据 perf 报告构建 [火焰图（flame graphs）](https://www.brendangregg.com/flamegraphs.html) 使其更清晰。你还需要考虑可能发生的函数内联（inline），这里 `std::lower_bound` 显然就是如此。Perf 也会跟踪共享库（如 `libc`）以及一般情况下任何其他衍生出的进程：如果你愿意，你可以用 perf 启动一个网页浏览器，看看其内部发生了什么。

接下来，你可以"放大"其中任意函数，除其他内容外，它会提供该函数的反汇编并附带一个关联的热力图。例如，下面是 `query` 的汇编代码：

```asm
       │20: → call   rand@plt
       │      mov    %r12,%rsi
       │      mov    %eax,%edi
       │      mov    $0xf4240,%eax
       │      nop    
       │30:   test   %rax,%rax
  4.57 │    ↓ jle    52
       │35:   mov    %rax,%rdx
  0.52 │      sar    %rdx
  0.33 │      lea    (%rsi,%rdx,4),%rcx
  4.30 │      cmp    (%rcx),%edi
 65.39 │    ↓ jle    b0
  0.07 │      sub    %rdx,%rax
  9.32 │      lea    0x4(%rcx),%rsi
  0.06 │      dec    %rax
  1.37 │      test   %rax,%rax
  1.11 │    ↑ jg     35
       │52:   sub    %r12,%rsi
  2.22 │      sar    $0x2,%rsi
  0.33 │      add    %esi,%ebp
  0.20 │      dec    %ebx
       │    ↑ jne    20
```

左列是指令指针停在某一特定行上的次数占比。你可以看到，我们约 65% 的时间花在了跳转指令上，因为它前面有一个比较运算符，表明控制流在那里等待该比较结果的确定。

由于 [[指令级并行.md|流水线（pipelining）]] 和乱序执行等复杂性，"现在"在现代 CPU 中并不是一个定义良好的概念，因此数据会略有不准，因为指令指针会向前漂移一点。指令级数据仍然有用，但在单个周期层面，我们需要切换到 [[程序模拟.md|更精确的工具]]。
