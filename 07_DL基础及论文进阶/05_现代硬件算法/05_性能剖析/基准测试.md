# 基准测试

大多数良好的软件工程实践，都在以某种方式解决"加快*开发周期*"这一问题：你希望更快地编译软件（构建系统）、尽早捕获缺陷（静态分析、持续集成）、在新版本就绪后立即发布（持续部署），并快速响应用户反馈（敏捷开发）。

性能工程也不例外。如果做得正确，它同样应当像一个循环：

1. 运行程序并收集度量指标。
2. 找出瓶颈所在。
3. 消除瓶颈，回到第 1 步。

在本节中，我们将讨论基准测试，并介绍一些能让这个循环更短、帮助你更快迭代的实用技巧。这些建议大多来自撰写本书过程中的经验，因此你可以在本书的[代码仓库](https://github.com/sslotin/ahm-code)中找到许多所述配置的真实示例。

### C++ 内部的基准测试

编写基准测试代码有若干种方法。或许最流行的一种，是把想要比较的多个同语言实现放进同一个文件，在 `main` 函数中分别调用它们，并在同一源文件中计算所有想要的度量指标。

这种方法的缺点在于需要编写大量样板代码，并为每个实现重复编写；不过这一点可以通过元编程部分抵消。例如，当你对多个 [[二进制 GCD.md]] 实现做基准测试时，用下面这个高阶函数可以显著减少基准测试代码：

```c++
const int N = 1e6, T = 1e9 / N;
int a[N], b[N];

void timeit(int (*f)(int, int)) {
    clock_t start = clock();

    int checksum = 0;

    for (int t = 0; t < T; t++)
        for (int i = 0; i < n; i++)
            checksum ^= f(a[i], b[i]);
    
    float seconds = float(clock() - start) / CLOCKS_PER_SEC;

    printf("checksum: %d\n", checksum);
    printf("%.2f ns per call\n", 1e9 * seconds / N / T);
}

int main() {
    for (int i = 0; i < N; i++)
        a[i] = rand(), b[i] = rand();
    
    timeit(std::gcd);
    timeit(my_gcd);
    timeit(my_another_gcd);
    // ...

    return 0;
}
```

这是一种开销极低的方法，让你能运行更多实验并从中 [[如何获得准确结果.md|获得更准确的结果]]。你仍需执行一些重复动作，但这些动作很大程度上可以用框架自动化，对 C++ 而言最流行的选择是 [Google benchmark 库](https://github.com/google/benchmark)。一些编程语言也带有方便的基准测试内建工具：此处特别值得一提的是 [Python 的 timeit 函数](https://docs.python.org/3/library/timeit.html) 和 [Julia 的 @benchmark 宏](https://github.com/JuliaCI/BenchmarkTools.jl)。

尽管 C 和 C++ 在执行速度上*高效*，但它们并非最*高效能（productive）*的语言，尤其是在分析处理方面。当你的算法依赖于某些参数（例如输入规模），并且需要从每个实现收集不止一个数据点时，你确实希望将基准测试代码与外部环节集成，并用其他工具分析结果。

### 拆分实现

改进模块化与可复用性的一种方法，是将所有测试与分析代码与算法的实际实现分离，并让不同版本以独立文件实现，但拥有相同的接口。

在 C/C++ 中，可以创建一个单独的头部文件（例如 `gcd.hh`），其中包含函数接口及其在 `main` 中的全部基准测试代码：

```c++
int gcd(int a, int b); // 待实现

// 对于数据结构，你还需要创建一个初始化函数
//（除非所有版本使用相同的预处理步骤就足够了）

int main() {
    const int N = 1e6, T = 1e9 / N;
    int a[N], b[N];
    // 注意：局部数组分配在栈上，可能导致栈溢出
    // 对于大数组，请用 "new" 分配或创建全局数组

    for (int i = 0; i < N; i++)
        a[i] = rand(), b[i] = rand();

    int checksum = 0;

    clock_t start = clock();

    for (int t = 0; t < T; t++)
        for (int i = 0; i < n; i++)
            checksum += gcd(a[i], b[i]);
    
    float seconds = float(clock() - start) / CLOCKS_PER_SEC;

    printf("%d\n", checksum);
    printf("%.2f ns per call\n", 1e9 * seconds / N / T);
    
    return 0;
}
```

然后为每个算法版本创建多个实现文件（例如 `v1.cc`、`v2.cc` 等，或在适用时使用有意义的名称），它们都包含那个单独的头部文件：

```c++
#include "gcd.hh"

int gcd(int a, int b) {
    if (b == 0)
        return a;
    else
        return gcd(b, a % b);
}
```

这样做的目的，是为了能够无需触碰任何源文件，就从命令行对某个特定算法版本进行基准测试。为此，你可能还希望把它的任何参数暴露出来——例如，通过从命令行参数中解析它们：

```c++
int main(int argc, char* argv[]) {
    int N = (argc > 1 ? atoi(argv[1]) : 1e6);
    const int T = 1e9 / N;

    // ...
}
```

另一种做法是使用 C 风格的全局宏定义，然后在编译时通过 `-D N=...` 标志传入：

```c++
#ifndef N
#define N 1000000
#endif

const int T = 1e9 / N;
```

这样你可以利用编译期常量，这对某些算法的性能可能非常有益；代价是每次想更改参数时都必须重新构建程序，这显著增加了跨一系列参数值收集度量指标所需的时间。

拆分源文件让你能够利用带缓存的构建系统（如 [Make](https://en.wikipedia.org/wiki/Make_(software))）来加速编译。

我通常在各个项目中沿用这样一个版本的 Makefile：

```c++
compile = g++ -std=c++17 -O3 -march=native -Wall

%: %.cc gcd.hh
	$(compile) $< -o $@ 

%.s: %.cc gcd.hh
	$(compile) -S -fverbose-asm $< -o $@

%.run: %
	@./$<

.PHONY: %.run
```

现在你可以用 `make example` 编译 `example.cc`，并用 `make example.run` 自动运行它。

你也可以在 Makefile 中加入计算统计的脚本，或将其与 `perf stat` 调用结合，使剖析自动化。

### Jupyter 笔记本

为加快高层分析，你可以创建一个 Jupyter 笔记本，把所有脚本放进去，并完成所有绘图。

为一个实现封装一个基准测试包装函数会很方便，它只返回一个标量结果：

```python
def bench(source, n=2**20):
    !make -s {source}
    if _exit_code != 0:
        raise Exception("Compilation failed")
    res = !./{source} {n} {q}
    duration = float(res[0].split()[0])
    return duration
```

然后你可以用它写出简洁的分析代码：

```python
ns = list(int(1.17**k) for k in range(30, 60))
baseline = [bench('std_lower_bound', n=n) for n in ns]
results = [bench('my_binary_search', n=n) for n in ns]

# 为不同数组规模绘制相对加速比
import matplotlib.pyplot as plt

plt.plot(ns, [x / y for x, y in zip(baseline, results)])
plt.show()
```

一旦搭建好，这套工作流能让你迭代快得多，并专注于优化算法本身。
