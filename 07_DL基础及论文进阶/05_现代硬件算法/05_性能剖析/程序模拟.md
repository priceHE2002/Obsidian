# 程序模拟

最后一种剖析方法（或者更确切地说，是一组方法）并非通过实际运行程序来收集数据，而是用专门的工具*模拟*它来推断应当发生什么。

此类剖析器有许多子类，区别在于模拟的是计算的哪个方面。在本文中，我们将聚焦于 [[RAM与CPU缓存.md|缓存（caching）]] 和 [[分支的代价.md|分支预测（branch prediction）]]，并为此使用 [Cachegrind](https://valgrind.org/docs/manual/cg-manual.html)，它是 [Valgrind](https://valgrind.org/) 中面向剖析的一部分；Valgrind 是一个成熟的工具，主要用于内存泄漏检测和一般性的内存调试。

### 使用 Cachegrind 进行剖析

Cachegrind 实质上是检查二进制中的"有趣"指令——即执行内存读/写以及条件/间接跳转的指令——并将它们替换为用软件数据结构模拟相应硬件操作的代码。因此它不需要访问源代码，可以处理已经编译好的程序，并可以像这样在任何程序上运行：

```bash
valgrind --tool=cachegrind --branch-sim=yes ./run
#       also simulate branch prediction ^   ^ any command, not necessarily one process
```

它对所有相关二进制插桩、运行它们，并输出一个类似于 [[统计采样剖析.md|perf stat]] 的摘要：

```
I   refs:      483,664,426
I1  misses:          1,858
LLi misses:          1,788
I1  miss rate:        0.00%
LLi miss rate:        0.00%

D   refs:      115,204,359  (88,016,970 rd   + 27,187,389 wr)
D1  misses:      9,722,664  ( 9,656,463 rd   +     66,201 wr)
LLd misses:         72,587  (     8,496 rd   +     64,091 wr)
D1  miss rate:         8.4% (      11.0%     +        0.2%  )
LLd miss rate:         0.1% (       0.0%     +        0.2%  )

LL refs:         9,724,522  ( 9,658,321 rd   +     66,201 wr)
LL misses:          74,375  (    10,284 rd   +     64,091 wr)
LL miss rate:          0.0% (       0.0%     +        0.2%  )

Branches:       90,575,071  (88,569,738 cond +  2,005,333 ind)
Mispredicts:    19,922,564  (19,921,919 cond +        645 ind)
Mispred rate:         22.0% (      22.5%     +        0.0%   )
```

我们喂给 Cachegrind 的正是与 [[统计采样剖析.md|上一节]] 完全相同的示例代码：我们创建一个包含一百万个随机整数的数组，对其排序，然后在其上进行一百万次二分查找。Cachegrind 显示的数字与 perf 大致相同，只是 perf 测量到的内存读和分支次数因 [[指令级并行.md|推测执行（speculative execution）]] 而略有膨胀：它们确实在硬件中发生、从而递增了硬件计数器，但随后被丢弃且不影响实际性能，因此在模拟中被忽略。

Cachegrind 只建模了缓存的第一级（`D1` 表示数据、`I1` 表示指令）和最后一级（`LL`，统一缓存），其特征由系统推断得出。它并不限制你，因为你也可以从命令行设置它们，例如，为建模 L2 缓存：`--LL=<size>,<associativity>,<line size>`。

它似乎到目前为止只是拖慢了我们的程序，而没有提供 `perf stat` 所不能给出的任何信息。要从中获取比摘要信息更多的东西，我们可以检查它默认转储在同一目录下的、名为 `cachegrind.out.<pid>` 的剖析信息特殊文件。它是人类可读的，但预期通过 `cg_annotate` 命令来阅读：

```bash
cg_annotate cachegrind.out.4159404 --show=Dr,D1mr,DLmr,Bc,Bcm
#                                    ^ 我们只关心数据读和分支
```

它首先显示运行期间使用的参数，包括缓存系统的特征：

```
I1 cache:         32768 B, 64 B, 8-way associative
D1 cache:         32768 B, 64 B, 8-way associative
LL cache:         8388608 B, 64 B, direct-mapped
```

它对 L3 缓存没完全搞对：它并非统一缓存（总计 8M，但单核只看到 4M），且是 16 路关联；不过我们暂时忽略这一点。

接下来，它输出一个类似 `perf report` 的逐函数摘要：

```
Dr         D1mr      DLmr Bc         Bcm         file:function
--------------------------------------------------------------------------------
19,951,476 8,985,458    3 41,902,938 11,005,530  ???:query()
24,832,125   585,982   65 24,712,356  7,689,480  ???:void std::__introsort_loop<...>
16,000,000        60    3  9,935,484    129,044  ???:random_r
18,000,000         2    1  6,000,000          1  ???:random
 4,690,248    61,999   17  5,690,241  1,081,230  ???:setup()
 2,000,000         0    0          0          0  ???:rand
```

你可以看到排序阶段有大量分支预测失败，二分查找期间也有大量 L1 缓存未命中和分支预测失败。这些信息我们用 perf 拿不到——它只会告诉我们整个程序的这些计数。

Cachegrind 拥有的另一个很棒的特性是源代码的逐行注解。为此，你需要用调试信息（`-g`）编译程序，并显式告诉 `cg_annotate` 要注解哪些源文件，或干脆传入 `--auto=yes` 选项，让它注解所有能触及的代码（包括标准库源代码）。

因此，完整的"源码到分析"过程会是这样：

```bash
g++ -O3 -g sort-and-search.cc -o run
valgrind --tool=cachegrind --branch-sim=yes --cachegrind-out-file=cachegrind.out ./run
cg_annotate cachegrind.out --auto=yes --show=Dr,D1mr,DLmr,Bc,Bcm
```

由于 glibc 的实现不是最易读的，为便于说明，我们用自己的二分查找替换 `lower_bound`，它会被这样注解：

