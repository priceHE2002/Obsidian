# 对齐与填充

内存被划分为 64 字节的[[缓存行.md|缓存行]]，这一事实使得操作跨越缓存行边界的数据字变得困难。当你需要获取某个基本类型（例如一个 32 位整数）时，你自然希望它位于同一条缓存行上——这既是因为获取两条缓存行需要更多的内存带宽，也因为用硬件拼接结果需要宝贵的晶体管面积。

这一方面深刻影响着算法设计，以及编译器如何选择数据结构的存储布局。

### 对齐分配

默认情况下，当你分配一个由某种基本类型构成的数组时，可以保证所有元素的地址都是其大小的整数倍，这就确保了它们只横跨一条缓存行。例如，可以保证 `int` 数组的第一个元素以及其后每个元素的地址都是 4 字节（`sizeof int`）的整数倍。

有时你需要确保这一最小对齐值更高。例如，许多[[SIMD并行.md|SIMD]]应用以 32 字节为块读写数据，而这些 32 字节属于同一条缓存行对于[[数据搬移.md|性能]]是至关重要的。在这种情况下，可以在定义静态数组变量时使用 `alignas` 说明符：

```c++
alignas(32) float a[n];
```

要动态分配一个内存对齐的数组，可以使用 `std::aligned_alloc`，它接受对齐值和数组的字节大小，并返回一个指向已分配内存的指针——就像 `new` 运算符一样：

```c++
void *a = std::aligned_alloc(32, 4 * n);
```

你也可以将内存对齐到[[内存分页.md|大于缓存行]]的尺寸。唯一的限制是大小参数必须是对齐值的整数倍。

你还可以在定义 `struct` 时使用 `alignas` 说明符：

```c++
struct alignas(64) Data {
    // ...
};
```

每当分配一个 `Data` 实例时，它都会位于一条缓存行的起始位置。缺点是该结构的有效大小会被向上取整到最接近的 64 字节整数倍。这样做是必要的，例如，在分配 `Data` 数组时，不仅是第一个元素能正确对齐。

### 结构体对齐

当我们需要分配一组非均匀的元素（结构体就是这种情况）时，问题会变得更复杂。与其像玩俄罗斯方块那样重新排列 `struct` 的成员、试图让每个成员都落在同一条缓存行内——这往往并不可行，因为结构体本身不一定被放置在缓存行的起始位置——大多数 C/C++ 编译器也依赖内存对齐这一机制。

结构体对齐同样确保所有成员基本类型（`char`、`int`、`float*` 等）的地址都是其大小的整数倍，这就自动保证了每个成员只横跨一条缓存行。它实现这一点是通过：

- 在必要时，为每个结构体成员填充数量不定的空白字节，以满足下一个成员的对齐要求；
- 将结构体自身的对齐要求设定为其各成员类型对齐要求的最大值，这样当分配该结构体类型的数组、或它被用作另一个结构体的成员类型时，其所有基本类型的对齐要求都能得到满足。

为了更好地理解，考虑下面这个示例性的例子：

```cpp
struct Data {
    char a;
    short b;
    int c;
    char d;
};
```

如果紧凑存放，该结构体每个实例需要共计 $1 + 2 + 4 + 1 = 8$ 字节，但即使假设整个结构体具有 4 字节对齐（其最大成员 `int`），也只有 `a` 是没问题的，而 `b`、`c` 和 `d` 并未按大小对齐，有可能跨越缓存行边界。

为修复这一点，编译器会插入一些未命名的成员，使得每个后续成员获得正确的最小对齐：

```cpp
struct Data {
    char a;    // 1 字节
    char x[1]; // 1 字节，用于让下面的 "short" 对齐到 2 字节边界
    short b;   // 2 字节 
    int c;     // 4 字节（最大成员，设定整个结构体的对齐）
    char d;    // 1 字节
    char y[3]; // 3 字节，使结构体总大小为 12 字节（可被 4 整除）
};

// sizeof(Data) = 12
// alignof(Data) = alignof(int) = sizeof(int) = 4
```

这可能会浪费空间，但能节省大量 CPU 周期。这种取舍大体上是有利的，因此结构体对齐在多数编译器中默认开启。

### 优化成员顺序

填充只会被插入到一个尚未对齐的成员之前，或结构体的末尾。通过改变结构体中成员的顺序，可以改变所需的填充字节数以及结构体的总大小。

在上面的例子中，我们可以这样重排结构体成员：

```c++
struct Data {
    int c;
    short b;
    char a;
    char d;
};
```

现在，它们每个都无需填充即可对齐，结构体大小仅为 8 字节。结构体的大小乃至其性能竟然取决于成员的定义顺序，这看起来很愚蠢，但这是二进制兼容性所必需的。

作为一个经验法则，类型定义应按照从最大数据类型到最小数据类型的顺序排列——这个贪心算法保证有效，除非你有一些奇怪的非 2 的幂的成员大小，例如[[IEEE 754 浮点数.md#IEEE 754 浮点数|10 字节]]的 `long double`[^extended]。

[^extended]: 80 位的 `long double` 至少占用 10 字节，但确切格式由编译器决定——例如，它可能会被填充到 12 或 16 字节，以最小化对齐问题（64 位 GCC 和 Clang 默认使用 16 字节；你可以通过指定 `-mlong-double-64/80/128` 或 `-m96/128bit-long-double` 等[选项](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html)来覆盖这一默认）。

### 结构体紧凑化

如果你很清楚自己在做什么，可以禁用结构体填充，并尽可能紧凑地打包数据。

你必须请求编译器来完成这件事，因为此类功能目前既不是 C 也不是 C++ 标准的一部分。在 GCC 和 Clang 中，可以使用 `packed` 属性来实现：

```cpp
struct __attribute__ ((packed)) Data {
    long long a;
    bool b;
};
```

这使得 `Data` 的实例只占用 9 字节，而不是对齐所要求的 16 字节，代价是读取其元素时可能需要获取两条缓存行。

### 位域

你还可以将紧凑化与*位域（bit fields）*结合使用，位域允许你显式地以比特为单位固定成员的大小：

```cpp
struct __attribute__ ((packed)) Data {
    char a;     // 1 字节
    int b : 24; // 3 字节
};
```

该结构体在紧凑化时占用 4 字节，在填充时占用 8 字节。一个成员拥有的比特数不必是 8 的整数倍，结构体的总大小也不必是。在 `Data` 数组中，相邻元素在字节数不为整数时会被"合并"。它还允许你设定超出基础类型宽度的位宽，这相当于填充——尽管在此过程中会抛出警告。

这一特性并不那么普及，因为 CPU 没有 3 字节的算术之类的运算，在加载时不得不进行一些低效的逐字节转换：

```cpp
int load(char *p) {
    char x = p[0], y = p[1], z = p[2];
    return (x << 16) + (y << 8) + z;
}
```

当存在非整字节时，开销更大，需要用移位和按位与掩码来处理。

这一过程可以通过加载一个 4 字节的 `int`，然后用掩码丢弃其高比特来优化。

```cpp
int load(int *p) {
    int x = *p;
    return x & ((1<<24) - 1);
}
```

编译器通常不会这样做，因为这在技术上是不合法的：那第 4 个字节可能位于一个你并不拥有的内存页上，因此即便你打算立即丢弃它，操作系统也不会允许你加载它。
